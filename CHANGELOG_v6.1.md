ZiziPlayer v6.1.0 — сборка починена + четыре реальных дефекта
v6.0 не собирался. Ниже — что именно ломалось, почему, и что ещё нашлось при полном
перечитывании кода.
1. Ошибка компиляции (тот самый красный крест)
e: Artwork.kt:167:52 Argument type mismatch: actual type is 'kotlin.Any',
   but 'android.graphics.Bitmap' was expected
Причина. В «быстром пути» получения обложки стоял elvis с разными типами по сторонам:
val fast = fastGate.withPermit {
    memory.get(cacheKey)          // Art?     — попадание в память
        ?: withContext(IO) { … }  // Bitmap?  — декодер
}
Единственный общий супертип Art? и Bitmap? — это Any. Kotlin вывел fast: Any, и следующая
строка finish(track, px, fast, …) (ждёт Bitmap) не скомпилировалась. Ровно одна ошибка на весь
проект — колонка 52 в логе указывает на fast.
Исправлено. Попадание в память теперь возвращает готовый Art сразу (withPermit — inline,
поэтому нелокальный return легален и permit всё равно освобождается в finally), а остаток
выражения имеет честный тип Bitmap?:
val fast: Bitmap? = fastGate.withPermit {
    memory.get(cacheKey)?.let { return it }
    withContext(Dispatchers.IO) { fromArtworkUri(…) ?: fromThumbnail(…) }
}
Перепроверка кеша под permit — не только ради типа: семафор нагружен, и пока корутина ждала
разрешения, другая могла уже декодировать ту же самую обложку.
2. Имена файлов кеша стоили дороже, чем чтение с диска
fileFor() вызывал "%02x".format(byte) — полноценный String.format — по разу на каждый из 20
байт SHA-1, плюс создавал новый MessageDigest. И делал это для каждого трека при проверке
isSettled, при чтении и при записи. На библиотеке в 3400 треков один проход индексатора платил
это десять тысяч раз.
Теперь: ручной hex по таблице символов + мемоизация дайджеста в LruCache(4096). Одна строка на
трек за всё время работы вместо сорока String.format на каждое обращение.
3. Кеш обложек рос сверх лимита до перезапуска
Ограничение в 40 МБ применялось только при старте. Полный проход индексатора мог оставить
каталог заметно больше лимита, и он жил таким до следующего запуска приложения. Добавлен
ArtworkCache.pruneNow() — вызывается по завершении прохода.
4. Уведомление невозможно было смахнуть на паузе
FLAG_ONGOING_EVENT ставился безусловно, поэтому уведомление оставалось несмахиваемым и после
паузы. Теперь флаг (вместе с зависящим от него FLAG_PROMOTED_ONGOING) выставляется только когда
плеер действительно играет, и снимается при паузе.
5. Падение в фазе отрисовки полосы прогресса
filled.coerceIn(thumb, size.width - thumb) бросает IllegalArgumentException, если min > max —
а это происходит на первом кадре с нулевой шириной или в очень узком окне. Исключение внутри
Canvas уносит весь экран. Границы теперь упорядочены явно.
6. Release-сборка: страховка на уровне R8
by viewModels() создаёт MainViewModel рефлексией. Правило -keepclassmembers для конструкторов
ViewModel приходит транзитивно из lifecycle, но приложение не должно зависеть от этой детали:
потеря конструктора — это крэш только в release, на первом кадре. Правило добавлено явно, как и
keep для ZiziApplication и для читаемого рефлексией поля FLAG_PROMOTED_ONGOING.
7. Предупреждения — в нуль
Мёртвые импорты, три неиспользуемые локальные переменные, устаревшая Icons.Filled.ArrowBack
(заменена на Icons.AutoMirrored.Filled.ArrowBack — попутно правильное поведение в RTL) и
рассинхрон exportSchema = false при заданном room.schemaLocation. Лог сборки теперь чистый,
и в нём видно только то, что действительно важно.
8. CI: зелёная галочка больше не врёт
Из build.yml убран continue-on-error — именно он делал провалившуюся сборку «успешной», а
отдельный шаг потом ронял джобу. Теперь:
собираются debug и release одной командой с --continue: если падает одна задача, вторая всё равно доводится до конца, и что-то устанавливаемое есть всегда;
шаг падает ровно тогда, когда падает сборка, а сводка ошибок пишется в Job Summary всегда;
APK и полный лог загружаются артефактами при любом исходе (if: always());
в сводке прямо сказано, что ставить нужно release.
versionCode 7, versionName 6.1.0.
