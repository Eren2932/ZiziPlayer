# ZiziPlayer 6.69.16 — выступ камеры, а не только обложки

28.09.2026 · **versionCode 141 · ZIP исходников, не APK.**
Основа: последний мобильный архив `ZiziPlayer-v6.69.15.zip` из публичного репозитория
Eren2932/ZiziPlayer, снимок `bc1ecdbf981d9b888f1458c3a6ecea805f626ecd`.
Это кандидат исправления с локальными проверками; Android-сборка и телефон ещё не проверены.

## Что было не так

В адаптере камеры оставалась подгонка из 6.69.10: для узкой системной области,
примыкающей к верхнему краю, диаметр вычислялся как `0.60 * width`, а нижняя граница
сдвигалась на `0.05 * width`. Это не данные Android и не правило Telegram — это
подгонка по отдельному видео. Она уменьшала фигуру и сдвигала её центр вниз.
Например, `Rect(508, 0, 572, 91)` превращался в круг диаметром 38.4 px с центром
(540, 68.6), вместо нижнепривязанного круга диаметром 64 px с центром (540, 59).

В GPU-пути камера затем размывалась радиусом 15 пикселей слоя, уменьшенного втрое,
точно как существенно большая обложка. После размытия общий порог отбрасывал
слабую прозрачность. Маленькая фигура камеры могла исчезнуть ещё до контакта:
обложка тянулась, но у камеры не оставалось собственного растущего выступа.
Исчезновение этого выступа воспроизведено в отдельной численной модели.
Это объясняет класс дефекта на фотографиях, но само по себе не измеряет реальную
камеру конкретного телефона: его сырые insets/контур в этом сеансе не получены.

## Исправление

Для узкой верхней области убраны коэффициенты 0.60/0.05. Приближение теперь — круг
с диаметром ширины системного Rect, нижней границей на его bottom и X из его центра.
Настоящий компактный `DisplayCutout.cutoutPath` имеет приоритет и не увеличивается
до reservation. Приближение по Rect по-прежнему явно обозначается как приближение,
а не как точная физическая калибровка. Широкие, неоднозначные и невалидные вырезы
не принимаются за одиночную фронтальную камеру.

Для слоя камеры введён собственный постоянный на весь жест радиус размытия:

`cameraBlur = min(15, min(cutoutWidth, cutoutHeight) / (4 * 3))`

Все размеры cutout здесь в пикселях окна; результат — в пикселях уменьшенного слоя.
Радиус обложки остался 15. Это целевая адаптация Zizi для маленьких реальных контуров,
**не утверждение, что такая формула есть в Telegram**. Два размытых слоя по-прежнему
складываются SrcOver и проходят один общий alpha threshold. Их нельзя пороговать
по отдельности — пропадёт жидкое соединение.

Треугольные заготовки, их пульс 0 → максимум → 0, затухание картинки, детализация,
линейное приближение к камере и финальное групповое исчезновение сохранены.
Не добавлены таймер, гистерезис, второй обработчик жеста или повторный экземпляр обложки.
В диагностическую трассу добавлен `cameraBlur`, чтобы на устройстве видеть реально
выбранный параметр вместе с прогрессом и координатами.

`PinnedCollectionScaffold` и `CollectionScrollPrecision` не менялись. Аудио, Media3,
Room, медиатека, аккаунты, сеть, серверы и desktop не затронуты. Android 8–11 остаётся
на прежнем геометрическом рендерере, но использует исправленный общий адаптер Rect.

## Что на самом деле делает публичный Telegram

Проверен коммит `dc780e81ed1261c369c27870e8e0999a1eb0b600`:

- `ProfileGooeyView.java`: актуальный GPU blur/threshold и CPU fallback.
- `ProfileActivity.java`: прогресс, перемещение и уменьшение аватара.
- `NotchInfoUtils.java`: чтение `config_mainBuiltInDisplayCutout` и разбор пути.
- `AndroidUtilities.java`: перегрузки lerp/ilerp.

В этом эффекте Telegram **не использует описанный универсальный getBoundingRects()-маршрут**.
Он читает системную строку конфигурации и в `ProfileGooeyView.onSizeChanged` отключает
notchInfo для бокового выреза и landscape. При отсутствии notchInfo в GPU-ветке есть
чёрная верхняя полоса; универсального обещания «аватар рядом с Back» этот код не даёт.
Старый `ProfileMetaballView` не является текущим подключённым рендерером.

В Zizi намеренно сохранены публичный `WindowInsets.displayCutout`, системный Path на
API 31+, поддержка левого/правого X и консервативные проверки системы координат.
Это перенос принципа с исправлениями для нашей архитектуры, не побайтовая копия и
не доказанное пиксельное совпадение на любом устройстве.

`getBoundingRects()` сообщает зарезервированные области, которые прошивка не обязана
делать точным контуром стекла. При спрятанном вырезе поведение OEM различается:
null/неподходящая геометрия или смещённое окно ведут к безопасному сворачиванию.
По одним safe insets нельзя универсально доказать, что пользователь включил чёрную
полосу. Существующий no-cutout fallback сохранён; отдельный новый перелёт к Back
в этой правке не реализован.

## Проверки

**Локально выполнено:** 79/79 скриптов `tools/test_*.py`, 518 Python unittest cases
(часть из них компилирует/исполняет production Java); полный `check_selftest.py`;
проверки импортов и баланса Kotlin; checker вызовов main и статических ссылок.
Новый JVM-набор: 6 318 утверждений о геометрии/радиусе. Мутация с возвратом старого
фиксированного радиуса отклоняется. Все существующие локальные регрессии проходят.

При запуске упрощённого checker вызовов на всём app/src остаются те же три предупреждения,
что и в исходном 6.69.15: CameraMorph6692UiTest.kt:519 и два LyricsHybrid*-теста.
В main подозрительных вызовов нет. Эти текстовые анализаторы не заменяют Kotlin compiler.

**Отдельная растровая модель:** 840 комбинаций параметров, 5 плотностей,
4 диаметра (8 / 12.33 / 20 / 32 dp), центр/лево/право, 7 положений жеста и 2 трактовки
радиуса Gaussian. Исходные вершины и параметры получены из production Java, не из
переписанной Python-версии геометрии. Старый радиус терял центр камеры в 720 комбинациях;
новый не потерял его ни в одной. Минимальная прозрачность ядра до порога — 0.683.
Это камера отдельно от обложки: обложка не может скрыть исчезновение камеры в тесте.
Модель не проверяет Compose clipping, GPU и аппаратные координаты. Картинка
`verification/v6.69.16/raster-model/camera-core-before-after.png` — схема, НЕ скриншот Android.

**Добавлены, но НЕ запускались:** 6 Android instrumentation-тестов. Четыре проверяют
выступ с неподвижной имитацией физического отверстия (центр/лево/право), связность
с обложкой при поглощении и исчезновение только программных пикселей. Два проверяют
левую/правую reservation и приоритет маленького точного Path над большим Rect.
Инвентарь CI теперь **API 28: 37, API 35: 51** обязательный тест.

**Не выполнено:** Gradle/Kotlin/Compose build, assemble APK, Gradle JUnit/instrumentation,
приёмка на телефоне, замеры FPS/GPU. В the Computer нет готового Android toolchain.
Нельзя выдавать локальную модель за подтверждение исправления на показанном устройстве.

## Как применить

Загрузить `ZiziPlayer-v6.69.16.zip` в корень Eren2932/ZiziPlayer. Существующий корневой
workflow сравнен с архивным: они совпадают и выбирают ZIP по максимальному versionCode.
Code 141 выше 140. Замена workflow или серверов не нужна. Не класть второй отличный ZIP
с тем же code 141. Для проверки камеры вручную запустить Actions с `run_camera_tests=true`.
Зелёный assemble сам по себе не означает, что прошли 37/51 Android-тестов.

После успешной сборки установить APK с прежней подписью поверх текущего, не очищая данные.
На телефоне проверить медленное вытягивание: сначала должен расти выступ у отверстия,
затем встречный выступ обложки и общий перешеек. При обратном ходе они должны разделяться
без плавающей точки; при полном сворачивании остаётся только физическая камера.
Проверить удержание 3–5 секунд, микрореверс, 60/120 Гц, повторное открытие подборки,
доступный режим скрытого выреза. Для боковой камеры — отдельное реальное устройство.

Если выступ остаётся смещённым, нужен копируемый отчёт существующей служебной диагностики
камеры (`raw rect`, `path bounds`, `systemPath`, `origin`, `density`) и короткое видео.
Дальше корректировать нужно конкретную систему координат/OEM-геометрию, а не снова
подбирать коэффициент диаметра по фотографии. Совпадение с физической камерой по одному
публичному Rect не гарантируется.
