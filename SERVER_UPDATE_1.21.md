# Серверное обновление 1.21-speed-rc1 (Reco 2.4-speed-rc1)

Цель: треки, аватары, обложки и рекомендации приходят быстро; подбор после выбора артистов не ждёт кнопки «Готово».
Клиент менять не нужно: схемы ответов те же. Лимит 200 треков на артиста остаётся потолком.

Статус: все тесты зелёные в песочнице на фикстурах. **На живом Deezer и на VPS не проверялось.** Цифры ниже — модель, не замер.

## Где терялось время

1. Новое TCP+TLS-соединение на каждый запрос (`requests.get` без `Session`): холодная страница артиста = 44 запроса = 44 рукопожатия.
2. Страница артиста ждала весь пул (до 4 с, 40 релизов), и только потом отдавала аватар, имя и треки.
3. Browse и Reco жили раздельно: без общего SQLite-кэша и без общего лимита 8 запросов/с. После перезапуска залп мог упереться в квоту Deezer и дать неполный пул.
4. Подбор по выбранным артистам начинался только после «Готово».
5. `/img`: после каждой новой картинки обход и `stat` всего кэша (квота 512 МБ), одинаковые запросы не склеивались.

## Что сделано

- **Keep-alive.** Общие `Session` для API и CDN.
- **Прогрев при выборе артиста.** Клиент уже шлёт `/reco/onboard?a=ID` на каждый тап. Теперь сервер в фоне кладёт в кэш всё нужное главной: карточку, радио (с запасным путём), граф, релизы и релизы 8 ближайших соседей. Ключи кэша те же, что у `_build`. Фон уступает живым запросам, не чаще раза в 30 мин на артиста.
- **Страница артиста.**
  - Ранняя отдача: ждёт первые 6 релизов по fans (подряд, без дыр) и поиск по имени.
  - Пока пул собирается: `total = null`, `next_offset` продолжается сразу за выданным (раньше короткая страница могла остановить пагинацию).
  - Сборка останавливается на 320 строках (вдвое больше потолка 200).
  - Готовый пул пишется в SQLite в урезанном виде и переживает перезапуск.
  - Browse и Reco делят кэш `album_tracks` и бакет 8/с.
- **Предсборка.** Для верхнего артиста поиска (запрос от 3 символов, не чаще раза в 4 с) и для каждого выбранного артиста.
- **Картинки.** Одно скачивание на ключ (остальные ждут), счётчик размера кэша вместо обхода, аватары онбординга, карточки главной и первые строки поиска кладутся на диск заранее (250 и 500 px).

## Модельные цифры

`python3 tools/bench_home.py <задержка_Deezer_с> <alive|dead> <секунд_на_выбор_артистов>` (из каталога `server/`).
Фейковый Deezer, реальный бакет 8/с, 7 артистов. Время `/reco/home` после выбора:

| Сценарий | Холодный (как было) | С прогревом, выбор 8 с | С прогревом, выбор 30 с |
|---|---|---|---|
| Deezer 0.2 с, радио живое | 3.6 с | 0.8 с | 0.2 с |
| Deezer 0.4 с, радио живое | 3.8–4.1 с | 1.8 с | 0.4 с |
| Deezer 0.2 с, радио мёртвое | 5.0 с, `complete=false` | 3.2 с | 0.2 с |

Вывод: выигрыш зависит от того, сколько человек выбирает артистов. Полный прогрев это 85–120 запросов при 8/с, то есть 10–15 с фоновой работы.
Если выбор занял 5–8 с, часть данных к «Готово» ещё не готова, и главная досчитывается по ходу. Это потолок бакета Deezer, а не код.

## Установка

Положите `server/` из ZIP на VPS (например, `~/zizi-1.21/server`).

```bash
# 1. Проверка. Ничего не пишет.
/opt/zizi/venv/bin/python ~/zizi-1.21/server/tools/deploy_server.py --check

# 2. Бэкап баз (WAL: копировать .db на ходу нельзя).
sqlite3 "$ZIZI_CATALOG_DB" ".backup '/opt/zizi/catalog.before-1.21.db'"

# 3. Установка (откат автоматический, если health не сошёлся).
sudo /opt/zizi/venv/bin/python ~/zizi-1.21/server/tools/deploy_server.py --apply

# Ручной откат
sudo /opt/zizi/venv/bin/python ~/zizi-1.21/server/tools/deploy_server.py --rollback /opt/zizi/server-backups/<папка>
```

Установщик принимает базы 1.19 и 1.20. Если на VPS файл правился руками, он откажется и покажет sha256.

## Проверка после установки

```bash
H="Authorization: Bearer $T"; B=https://<ваш-хост>
curl -s -H "$H" $B/catalog/health | jq '.version'            # "1.21-speed-rc1"
curl -s -H "$H" $B/reco/health | jq '{version, bg_calls, warmed, warming, bucket}'
curl -s -H "$H" $B/reco/probe                                   # живо ли радио Deezer
time curl -s -H "$H" "$B/catalog/browse/collection?..." -o /dev/null   # холодная страница артиста
```

Нужны от вас выводы `/reco/probe` и `/reco/health` до и после установки — по ним сравним реальные цифры.

## Риски

- Прогрев и предсборка делят бакет 8/с с живыми запросами. Приоритет у людей, но под нагрузкой смотрите `bg_calls` и `bucket`.
- Страница 2 артиста может слегка переупорядочиться относительно ранней страницы 1. Клиент дедуплицирует по id, редкий пропуск возможен.
- Gzip не включали: нельзя на `/stream` и `/img`, а `zizi_resolver.py` под печатью.
- `test_probe_contention` нестабилен по времени (падал раз на исходном коде, в последнем прогоне зелёный).
- Тесты `test_catalog_wiring`, `test_zizi_device`, `test_zizi_guard` запускаются не как `unittest` (0 тестов при таком запуске); их гоняет установщик своим способом.
