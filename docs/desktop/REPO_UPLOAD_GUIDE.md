# Как разместить Desktop 0.2.0-preview в ZiziPlayer

## Рекомендованный вариант

Оставить один репозиторий Eren2932/ZiziPlayer. Не создавать второй только ради предотвращения ошибок Actions. Разделить файлы, workflow и release namespace. Пакет не содержит изменений мобильного исходного ZIP и не переносит серверные/подписывающие секреты в Desktop.

## Шаг 1. Обновить Android workflow

Из пакета взять `.github/workflows/build.yml` и заменить **именно корневой** файл с этим путём. Не помещать его внутрь мобильного ZIP. Сначала сравнить diff `docs/desktop/android-ci.diff`; baseline и SHA-256 записаны в ci-baseline.json. Если upstream build.yml с момента подготовки изменился, переносить изменения по diff, а не затирать новые мобильные шаги старой полной копией.

Можно сделать через GitHub → .github/workflows/build.yml → Edit и вставить содержимое. Предпочтительно сначала просмотреть изменение в отдельной ветке/PR. Автоматический PR-trigger в этом workflow не добавлен. После merge в main изменение build.yml намеренно вызовет Android-сборку — это проверка, что существующий мобильный цикл сохранился.

Существующий ZIP selector и проверки сохранены. В корне поддерживается прежняя схема мобильных архивов, но автоматический push-trigger теперь ожидает имя `ZiziPlayer-v*.zip`. Для мобильного архива с другим именем потребуется переименование или ручной запуск Actions.

## Шаг 2. Добавить Desktop и документацию

Перенести из распакованного пакета следующие каталоги с сохранением структуры:

````text
.github/workflows/desktop.yml
ci/extract_desktop.py
desktop/current.json
desktop/releases/ZiziDesktop-0.2.0-preview-source.zip
docs/desktop/
````

`desktop/current.json` — точный указатель на исходный ZIP и его SHA-256. Он не пытается угадать «последнюю» версию по имени или дате. При следующем обновлении Desktop меняются ZIP, version, source_zip, sha256 и project_directory. Для существующего архива 0.2.0-preview значения уже правильные.

**Не загружать внешний упаковочный ZIP целиком в корень и не считать это установкой workflow.** GitHub не запускает .github/workflows, спрятанный внутри ZIP. Распаковать пакет и загрузить его содержимое в соответствующие пути. Сам исходный Desktop ZIP, напротив, должен остаться ZIP-файлом в desktop/releases: его извлекает Windows workflow.

Не заменять мобильный `ZiziPlayer-v6.39.9.zip` настольным архивом и не переносить сейчас мобильный архив из корня. Папки .github и desktop — разные уровни назначения, это важно при загрузке через веб.

## Шаг 3. Первый Windows CI

После попадания workflow в default branch: Actions → **Build Zizi Desktop Windows preview (manual)** → Run workflow. Никакие Android secrets ему добавлять не нужно.

При успехе появятся два Actions artifacts: Windows app-image с EXE/Java runtime и тестовые отчёты. Это не опубликованный GitHub Release. При ошибке нужно скачать test-reports и изучить desktop-build.txt; первыми внешними рисками являются установка Chocolatey FFmpeg и различия Windows runner.

Версии JDK, Gradle, Kotlin и Compose заданы явно. FFmpeg в первом CI не закреплён по версии и устанавливается только для тестов; после первого успешного прогона следует закрепить поставку. Работоспособность нового workflow в GitHub ещё не подтверждена. Это отдельный шаг от уже успешной локальной сборки пользователя.

## Шаг 4. Если нужен публичный Desktop Release

Использовать тег **`desktop-v0.2.0-preview`**, а не `v0.2.0`. Создавать тег на commit, в котором уже есть обновлённый корневой build.yml. Если поставить тег на старый commit, старый workflow может реагировать по старым правилам.

Назвать релиз, например, «Zizi Desktop 0.2.0 Preview». Пометить Pre-release. Приложить исходный ZIP; при наличии проверенной бинарной поставки — отдельный ZIP **всего app-image**, а не одиночный ZiziDesktop.exe. В описании отметить внешний FFmpeg, отсутствие pause/seek/полной медиатеки и технический характер дизайна.

Бинарная пользовательская папка в подготовленном пакете отсутствует: ассистент её не получал. Исходный ZIP — не EXE-дистрибутив. Добавление Release asset не помещает исходники в ветку; используемый CI читает архив из checkout по desktop/current.json.

Новый desktop workflow автоматически Releases не создаёт и файлы к ним не прикрепляет. Это сознательно консервативный первый этап CI.

## Что будет запускаться после обновления

| Событие | Android workflow | Desktop workflow |
|---|---|---|
| Push только handoff/.md | Не запускается по paths | Не запускается |
| Push только desktop/releases или desktop/current.json | Не запускается по paths | Не запускается: пока manual |
| Push мобильного ZiziPlayer-v*.zip в main/master | Собирает APK | Не запускается |
| Push изменения .github/workflows/build.yml в main/master | Собирает APK | Не запускается |
| Push Android-тега v6.40.0 | Собирает APK | Не запускается |
| Publish Android Release v6.40.0 | Собирает/прикрепляет APK | Не запускается |
| Push тега desktop-v0.2.0-preview | Не запускается по tag filter | Не запускается |
| Publish Desktop Release desktop-v0.2.0-preview | Workflow может отображаться как skipped: job не выполняется | Не запускается |
| Run workflow для Desktop | Не затрагивается | Проверяет исходник, тестирует и пакует Windows app-image |
| Run Android workflow с attach_to_tag=desktop-v… | Останавливается на валидации namespace | Не затрагивается |

Path-фильтры относятся к push веток; они не защищают release и tag events сами по себе. Поэтому предусмотрены отдельные правила тегов и job guard.

Историческое поведение Android — запуск и на tag push, и на published release — оставлено. При обоих событиях возможны отдельные прогоны; дедупликация релизного цикла не была целью этой правки.

Если Android workflow/check настроен как обязательный status check для каждого PR, path-filtered skip может оставить ожидание required check. Тогда нужно отдельно скорректировать branch protection или добавить постоянно запускающийся routing/check workflow. В пакете правила защиты веток не меняются.

## Что не переносить в исходный ZIP/репозиторий

Не включать .gradle, .tools, build/dist с локальными бинарниками в исходный ZIP, кеши, личные треки, пользовательские логи, .local-runtime.json, signing keystore, токены и пароли. Бинарный app-image распространять отдельно, вместе с необходимыми лицензиями. FFmpeg сейчас не bundled; выбор его бинарной поставки и лицензии остаётся отдельным решением.

## Как не потерять защиту позже

Корневой `.github/workflows/build.yml` — действующая точка управления APK Actions. Старая копия workflow внутри очередного мобильного ZIP не должна автоматически перезаписывать её. Изменения мобильного CI нужно объединять с namespace/path-защитой этого пакета, сохраняя новые проверки, а не откатывать всю конфигурацию.

Подробное состояние приложения, подтверждения и ограничения находятся в HANDOFF_DESKTOP_0.2.0.md. Результаты выполненных здесь локальных проверок CI — в VALIDATION_CI.txt. GitHub-hosted CI и YAML-парсер в этих проверках не запускались.
