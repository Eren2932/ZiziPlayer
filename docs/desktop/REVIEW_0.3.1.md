# Разбор ZiziPlayer: Desktop 0.3.0 и Android 6.39.9

Дата: 2026-09-08. Источник: публичный репозиторий Eren2932/ZiziPlayer, main, полученный в этой сессии. GitHub Releases API показывает APK v6.39.9 от 2026-09-07. Для анализа использованы последние исходные ZIP из main: `ZiziDesktop-0.3.0-repo-update.zip` → `desktop/releases/ZiziDesktop-0.3.0-preview-source.zip` и `ZiziPlayer-v6.39.9.zip`. Бинарный APK не декомпилирован: доступные исходники дают гораздо больше архитектурной информации. Их тождество содержимому опубликованного APK не подтверждено воспроизводимой сборкой.

## Архитектура и степень общности

Android — Kotlin/Jetpack Compose, MainViewModel/SearchViewModel, Room/репозиторий, Media3, OkHttp и серверные каталоги/resolve. Основные сетевые узлы: `ZiziResolve`, `ZiziInstall`, `ZiziHttp`; сервер — Python/FastAPI и guard/catalog/resolve/stream. Поиск имеет отдельные HUB / RECENT / SUGGEST / RESULTS, страницы коллекций, пагинацию и сохранение музыки.

Desktop — Kotlin/JVM 21, Compose Desktop 1.7.3, один DesktopUi, отдельный DesktopPlayer с поколениями сессии, FFmpeg → PCM → общий DSP → JavaSound. Доступ к каталогу/resolve — HttpURLConnection, аудио передаётся FFmpeg через локальный StreamBridge. Bridge сохраняет Range/HEAD и не передаёт токен в аргументы процесса. Медиатека и очередь десктопа пока не равны Android Room: список добавленных файлов живёт в сессии.

Оригинальные `Biquad`, `DspConfig`, `DspEngine`, `DspPresets` и `ZiziIcons` уже были перенесены в 0.3.0 побайтно. Их хеши сохранены и проверены. То есть проблема внешнего вида не в отсутствии мобильных иконок, а в компоновке, стандартных контролах и теме. В 0.3.1 добавлена побайтная копия платформонезависимой `SearchPresentation` с проверкой хеша.

Это пока синхронизация контрактов и отдельных общих файлов, не единый Kotlin Multiplatform-модуль. Следующий архитектурный шаг — общий модуль моделей/auth policy/search presentation/design tokens с платформенными adapters для хранения, HTTP и воспроизведения. Нельзя считать две изменяемые копии «единой логикой» навсегда.

## Почему подключение 0.3.0 могло не работать

`network/ZiziClient.kt`, `HttpTransport.safeUri` разрешает HTTPS и HTTP loopback, но не внешний HTTP. Android `ZiziResolve.base()` добавляет HTTP к адресу без схемы. Это подтверждённое отличие кода, но скриншот сам по себе не содержит сообщения об ошибке, поэтому единственная фактическая причина сбоя на компьютере пользователя не установлена.

В `DesktopMain.kt` у 0.3.0 `client` изначально null. Серверный адрес читается из Preferences, но клиент создаётся только в `connect()` при применении настроек. Bootstrap не сохраняется, а применение диалога всегда заменяет клиента, даже если меняли только путь FFmpeg. Отсюда неудобный обязательный ручной ввод и потеря настроенной авторизации.

0.3.1 получает endpoint/bootstrap из ресурса, формируемого Gradle из тех же GitHub inputs, что использует Android. Сеть прогревается на IO, а не в Compose. На холодном запросе обмен ключа выполняется синхронно внутри IO, что намеренно отличается от Android фонового fallback: сервер в `require` может отвергнуть bootstrap до окончания асинхронного обмена. При 401 по сохранённому device-ключу добавлена одна ограниченная попытка обновления и повтора JSON-запроса. Range/HEAD/redirect policy сохранены.

## Что реально защищает сервер

В `server/zizi_guard.py` `_device_key()` использует независимый `ZIZI_DEVICE_KEY`, **только если он задан**. Иначе ключ подписи детерминированно выводится из `ZIZI_CATALOG_TOKEN` либо `ZIZI_TOKEN`. Если этот bootstrap известен из публичного клиента, предположение «секрет подписи отсутствует в приложении и не восстанавливается из него» в fallback-конфигурации неверно. Это вывод из реализации, не проверка действующего VPS.

Кроме того, `device_mode()` по умолчанию возвращает `warn`: это совместимость со старыми APK, а не строгий запрет общего bearer. В режиме `require` сервер умеет принимать bootstrap только для `/auth/device`, защищать рабочие маршруты device-ключом, учитывать подписанный ID и отзывать установку. Ограниченная квота выдачи остаётся важна: новый UUID сам по себе не является доказательством уникального устройства.

Для укрепления нужно на стороне VPS задать независимый случайный `ZIZI_DEVICE_KEY`, сохраняемый только в серверном окружении; защитить API HTTPS; проверить выдачу/обновление/401 на обеих платформах и лишь затем планировать `ZIZI_DEVICE_MODE=require`. Подпись/ключ и реальные env в отчёт не включены; действующие параметры не считаны и не изменены. Переход на независимый ключ делает старые device-токены недействительными, поэтому требует контролируемого окна и проверки восстановления Android.

У Android 6.39.9 `ZiziInstall.bearer()` возвращает bootstrap и обновляет device-ключ в фоне, когда ключ ещё не получен либо уже подходит к порогу обновления. Это потенциальное окно 401 в строгом режиме. Нельзя просто включить `require` и объявить обе платформы проверенными без тестирования этого сценария. Пакет desktop не меняет сервер и APK.

Скрытое поле не является защитой ключа. Даже secret из GitHub Actions станет извлекаемым bootstrap внутри опубликованного бинарника. Именно сервер должен ограничивать его полномочия; серверный ключ подписи туда попадать не должен. HTTP даже с origin-проверкой оставляет bearer и трафик доступными для перехвата на пути.

## Дизайн и анимации

Android `ZiziTheme.kt` разделяет нейтральную AMOLED-базу и цветной режим обложки, использует Oklab/Oklch и ArtworkColorMath; `BackdropBlend` владеет переходом, а `PlayerTransitionPolicy` согласует его с треком и жестом. Это существенно сложнее среднего RGB обложки, наложенного на двухцветный вертикальный градиент Desktop 0.3.0.

Большой тёмный градиент может давать banding из-за квантования небольшого диапазона оттенков на большой площади. Снимок экрана и код не позволяют исключить вклад дисплея/гаммы/вывода. В 0.3.1 градиент удалён: сплошной #000000, поверхности #101010, chips #1B1B1B, основной текст #F6F7F8, вторичный #9A9A9A, бренд #F97316. Убрана ненужная усреднённая RGB-палитра и стандартный surface tint диалогов. Для матового режима нечему образовывать ступени градиента; это не обещание устранить аппаратные особенности экрана.

Поле поиска адаптировано по `SearchScreen.kt`: 49.5/52 dp, угол 3.5 dp, белый idle и #292929 при вводе, текст 17 sp. Перенесена логика вращения Refresh: 900 ms линейно, затем 340 ms до полного оборота с FastOutSlowInEasing. Есть история запросов и подсказки истории/локальных названий, но не выдача provider suggestions. Показ/скрытие DSP-панели анимированы; это desktop-адаптация, не перенос всей мобильной системы жестов.

Полный мобильный хаб с жанрами, реальными полками, коллекциями и пагинацией; now-playing overlay/миниплеер и жестовые переходы; арт-палитра и её handoff; постоянная медиатека/сохранение коллекций пока НЕ перенесены. Визуальный паритет 1:1 не достигнут и в этом пакете не заявляется. Typography использует платформенные шрифтовые defaults, поэтому идентичность метрик также не подтверждена.

## Проверки и ограничения

Выполнены: 21 статический контракт с проверкой шести upstream-хешей; 9 Python-тестов preflight; проверка строк/скобок/Kotlin-комментариев (не компиляция); 46 утверждений оригинального серверного `test_zizi_device.py` на локальных fixtures. Последние подтверждают контракт исходников, не защищённость текущего VPS. ZIP manifest/hash/extraction дополнительно проверены при упаковке.

Добавлены 9 JUnit-методов проверки bundled config, scoped HTTP, кэша и восстановления 401. Всего в исходниках 44 JUnit-метода вместе с существующими аудиотестами. Kotlin/Gradle/JUnit/Windows app-image в этой сессии НЕ запускались. Нет проверки живого сервера, прослушивания, screenshots новой сборки или визуального теста. GitHub Actions должен выполнить сборку и все JUnit/audio-тесты перед использованием.
