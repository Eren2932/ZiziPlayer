# ZiziPlayer Desktop — состояние 0.2.0-preview и план продолжения

**Дата фиксации:** 8 сентября 2026 года.  
**Мобильная база:** ZiziPlayer Android 6.39.9, versionCode 81.  
**Настольная база:** Zizi Desktop 0.2.0-preview; предыдущий аудиостенд — Zizi Audio Lab 0.1.0.  
**Платформа проверки:** Windows пользователя; архитектура поставки ориентирована на Windows x64. Точная версия ОС и модель звукового устройства в этой фиксации не записаны.  
**Статус:** техническая возможность нативного настольного приложения подтверждена локальной сборкой и ручным прогоном. Полного функционального и визуального соответствия Android пока нет.

## 1. Коротко: где находится проект

ZiziPlayer уже существует как стабильнее работающий мобильный продукт на Kotlin/Android после отказа от Flutter. Для Windows выбран Kotlin/JVM + Compose Multiplatform Desktop, без эмулятора Android и без возврата к Flutter.

За текущую сессию создан сначала консольный аудиостенд, затем отдельное окно Compose Desktop. Пользователь собрал и запустил оба на Windows. В последнем подтверждённом прогоне файл с русским названием открывается через системное окно, музыка играет, эффекты меняются во время воспроизведения, упаковка GUI-приложения в EXE проходит.

**Текущий внешний вид — инженерный прототип, не утверждённый дизайн Zizi Desktop.** Мобильное приложение значительно дальше по визуальной проработке. Наличие окна, оранжевых элементов и эквалайзера нельзя считать завершённым переносом интерфейса.

Android-проект при создании настольных прототипов не менялся. Десктоп не добавлен внутрь мобильного Gradle root. Коммиты, ветки и релизы в GitHub в ходе этой работы ассистентом не создавались: подготовлены скачиваемые исходники, документация и предлагаемая настройка CI.

## 3. Принятые архитектурные решения

Язык настольной версии — Kotlin/JVM. UI — Compose Multiplatform Desktop, не WebView и не Electron. Windows EXE создаётся как запускатель приложения с упакованной Java-средой. Пользователю готовой поставки не требуется отдельно устанавливать JDK, но для сборки исходников нужен JDK 21.

Выбрана отдельная настольная сборка, чтобы не повредить работающий Android. На текущем этапе часть аудиокода скопирована в независимый проект. Это временный способ изоляции, а не утверждение, что копии следует поддерживать бесконечно. После стабилизации контракта воспроизведения целесообразно выделить общий `audio-core` и отдельно платформенные адаптеры.

Android Media3/ExoPlayer не используется в Windows-версии. Общим ресурсом является собственная DSP-математика, а не Android-сервис воспроизведения.

Целевая логическая структура:

````text
Общие модели и правила
    идентификаторы треков, очередь, DSP, пресеты, правила состояния
    переносимые визуальные компоненты и формат обмена плейлистами

Android adapter
    Media3, MediaStore/SAF, Android services, Room/настройки в текущем виде

Desktop adapter
    декодирование PCM, управление аудиовыводом, файлы Windows
    самостоятельное хранение, UI Compose Desktop, системная интеграция
````

Это целевая структура. В 0.2.0-preview полноценные общие модули доменной логики и новый DesktopPlayer ещё не выделены.

## 4. Аудиотракт, который уже работает

````text
Локальный файл / прямой HTTP(S)-источник
                ↓
FFmpeg как отдельный процесс декодирования
                ↓
Float PCM, little-endian, 48 000 Гц, 2 канала
                ↓
Ограниченная очередь PCM + предварительное накопление
                ↓
Оригинальный DspEngine из Android 6.39.9
                ↓
Громкость, преобразование в PCM16
                ↓
Java Sound / SourceDataLine → системное устройство вывода
````

Обработка идёт блоками по 1024 PCM-кадра, очередь ограничена примерно двумя секундами. GUI использует предварительное накопление 500 мс и запрос выходного буфера 250 мс. Это инженерные начальные значения, не оптимальные параметры для всех драйверов.

Декодер и аудиопоток не работают внутри отрисовки Compose. DSP принадлежит одному аудиопотоку. UI передаёт неизменяемую конфигурацию через `Controls.config`, а не вызывает `DspEngine.process` напрямую. CSV-диагностика записывается отдельным потоком, чтобы файловые операции не тормозили звук.

Четыре сохранённых файла: `Biquad.kt`, `DspConfig.kt`, `DspEngine.kt`, `DspPresets.kt`. Windows-обвязка — `Decoder.kt`, `Pcm.kt`, `Sink.kt`, `Engine.kt`; в GUI-прототипе они перенесены из генератора Audio Lab без изменения логики.

FFmpeg **не выполняет вместо нас эффекты Zizi**: он декодирует. Java Sound — стартовый адаптер вывода, не окончательная гарантия минимальной задержки, WASAPI exclusive или бесшовной смены устройств. Переход на другой вывод возможен за интерфейсом Sink при подтверждённой необходимости.

## 5. Хронология этапов и исправленных проблем

### 5.1. Анализ мобильной версии

Исследованы актуальный ZIP, последние изменения, DSP, основные экраны, тема, иконки, модели медиатеки и сетевые зависимости. Подтверждено, что порт на Windows реален, но не является преобразованием APK в EXE.

### 5.2. Audio Lab 0.1.0

Подготовлены отдельный Gradle-проект, локальный/HTTP-декодер, Java Sound и WAV sink, четыре простых стендовых пресета, диагностические CSV и 18 тестов. Пользователь начал сборку на Windows.

Первый сбой произошёл при распаковке Gradle 8.11.1 стандартным PowerShell `Expand-Archive`: внутри Microsoft.PowerShell.Archive возникла ошибка `Remove-Item` об отсутствующем `gradle-8.11.1/LICENSE`. По этому сообщению нельзя доказать точную первопричину; ошибка могла возникнуть при очистке после неудачной распаковки.

Подготовлен `Build.GradleFix.ps1`: `.NET ZipFile.ExtractToDirectory`, проверка SHA-256, повторное использование корректного ZIP, распаковка в новый staging-каталог, сохранение предыдущей папки Gradle и маркер успешной распаковки. Пользователь заменил Build.ps1; далее получил `BUILD SUCCESSFUL`.

### 5.3. Первый слышимый Windows-сеанс

Пользователь подтвердил музыку и эффекты в консоли, затем упаковку `ZiziAudioLab.exe`. На скриншоте финального сеанса: 3 929 088 PCM-кадров, sourceWaitEvents=0, deviceEmptyHints=0, clippedSamples=0, maxDspMs=4.969. Это около 82 секунд аудио, не многочасовой стресс-тест.

Счётчик deviceEmptyHints — косвенная диагностика, **не измерение WASAPI xrun**. Нулевые показатели не доказывают отсутствие всех слышимых артефактов.

### 5.4. Проблема русских имён в консоли

Вначале был введён путь к папке вместо файла — это не поддерживается текущим декодером. При вводе пути с кириллицей затем возник `MalformedInputException`. Переименование файла позволило продолжить.

Рабочая гипотеза — декодирование консольного ввода, а не неспособность Windows или FFmpeg работать с Unicode. Точная первопричина консольного сбоя отдельно не установлена. Изменять глобальную кодовую страницу Windows для всего продукта не принято как решение.

### 5.5. GUI 0.2.0-preview

Создан независимый Compose Desktop проект. Файл выбирается через `JFileChooser`; строка пути передаётся в `ProcessBuilder` без shell и без консольного ввода. Подключены фирменные иконки, группы настоящих мобильных DSP-пресетов и эквалайзер.

В набор добавлен девятнадцатый аудиотест: путь с кириллицей и пробелами через реальный декодер/DSP. Сборочный скрипт требует FFmpeg-интеграционные тесты до запуска/упаковки. Полный JUnit-отчёт последнего GUI-прогона в диалог не загружался; отдельно утверждать, что изучен отчёт о прохождении всех 19 тестов, нельзя.

**Сообщение пользователя после запуска:** русское название открывается через системное окно, эффекты меняются на лету, EXE упакован. Скриншот подтверждает открытое окно Compose с выбранным файлом и элементами DSP. Слышимость эффектов подтверждена сообщением пользователя, не изображением.

## 7. Важные ограничения текущего кода

`DesktopSession` — временный контроллер внутри `DesktopMain.kt`. Observable-состояние меняется на UI-потоке; текущий аудиосеанс работает отдельно. При переключении транспорт временно блокируется, пока освобождается старый сеанс. Это простая защита прототипа, не финальная политика быстрых команд.

Статус «загрузка / воспроизведение» не различает точный момент начала слышимого звука. Итоговые метрики появляются после остановки/завершения. Реального потока позиции нет, поэтому в UI намеренно отсутствует фиктивный seek bar.

Prev/next следует порядку добавления, а не текущему поисковому фильтру. Список находится только в памяти. Один щелчок запускает файл с начала. Stop не является паузой; кнопка «С начала» именно перезапускает, а не продолжает.

Общий DSP действует на сеанс; мобильное сохранение отдельного профиля трека и глобального режима ещё не перенесено. Некоторые ползунки включают DSP при изменении; это поведение нужно привести к единой утверждённой UX-модели позднее.

Ошибка отображается безопасно, без исходного URL, но детализация причин пока слабая. Секретные URL нельзя вводить в текущий HTTP-стенд: полный адрес виден в аргументах процесса FFmpeg. Закрытие/отмена во время медленной сети, быстрые команды и зависшие драйверы требуют отдельных тестов.

## 8. Что важно перенести из Android, а не придумать заново

В `PlayerController.kt` уже есть полезное разделение структурного состояния и прогресса. `Progress.trackId` защищает от чужой позиции при смене трека. Desktop должен сохранить этот принцип и добавить идентификатор поколения сеанса для отбрасывания поздних событий отменённого декодера.

В `EqualizerScreen.kt` состояние DSP одно: UI читает конфигурацию, команды меняют её через контроллер. Нельзя создавать несвязанные «ползунки для красоты» со второй копией состояния. Спектроанализатор в Android включается при необходимости — его не следует постоянно считать ради закрытой панели.

`ZiziTheme.kt` разделяет постоянный брендовый оранжевый #F97316 и цветовой акцент текущей обложки. Мобильный визуальный характер — тёмная основа, согласованные поверхности, собственные иконки, цвет обложки и управляемые переходы. Простая оранжевая раскраска Material-компонентов этого не заменяет.

`LibraryFilter` включает COLLECTION/TRACKS/FAVORITES/PLAYLISTS/FOLDERS/ARTISTS. Room-сущности содержат source, provider/remoteId, savedAt, lastSeenAt. Важное правило: прослушанный удалённый трек не становится сохранённым автоматически.

`StreamResolver` разворачивает zizi:// непосредственно перед загрузкой. `ZiziInstall` и `/auth/device` участвуют в учёте установки/ключах. `SessionWebToken` зависит от Android WebView; его нельзя просто вставить в JVM-проект. Фактическая конфигурация работающего сервера в этой сессии не проверена.

`PlaylistShare` описывает .zizi как JSON и текстовый транспорт `ZIZI1:base64(gzip(json))`. Это данные о треках, а не файлы музыки. Совместимость формата требует замены Android-кодеков и тестов; автоматическая синхронизация устройств из наличия общего сервера не следует.

## 9. Дизайн: почему сейчас «небо и земля» и что делать

Текущий экран специально делался для проверки связи UI со звуком. Он использует стандартные кнопки и длинную колонку ползунков; в списке только имена файлов, нет обложек, карточек, реальной коллекции и тонкой работы с цветом. Это технический долг прототипа, а не направление финального дизайна.

Целевая компоновка: боковая навигация, центральная коллекция/список, постоянная нижняя панель воспроизведения, опциональная боковая очередь или панель звука. Не нужно навсегда занимать треть окна эквалайзером. Пользовательский сценарий «слушаю и выбираю музыку» важнее сценария «кручу DSP».

Для следующего дизайн-прохода нужны токены поверхностей, отступов, типографики, радиусов и состояний наведения/фокуса; desktop-версии карточки трека, заголовка коллекции, панели транспорта и большого плеера. Фирменные векторы переиспользуются. Обложка и цветовая математика подключаются после источника метаданных и кэша.

Приёмка должна включать клавиатуру, правый клик, колесо, видимый фокус, масштаб Windows 100/125/150/200%, минимальный размер окна и длинные названия. Изменение размеров окна не должно задерживать звук. Мобильную геометрию и жесты Android не растягиваем на монитор.

## 10. Следующие этапы и критерии готовности

### A. Контракт движка и транспорт

Выделить DesktopPlayer за интерфейсом; состояние и прогресс — отдельные StateFlow. Ввести trackId/session generation, сериализованные команды и отмену старых операций. Реализовать pause/resume, seek, автопереход, next/previous и EOF/error как разные исходы.

Пауза должна сохранять позицию и управлять выводом/очередью, а не глушить громкость. Перемотка должна отменять старый декодер, очищать относящиеся к нему буферы, запускать источник с новой позиции и публиковать подтверждённый прогресс. Учесть задержку устройства; счётчик декодированных кадров не равен слышимой позиции.

Приёмка: быстрые повторные команды без чужой обложки/позиции, seek около начала/конца, отмена загрузки, конец файла, pause/resume без самопроизвольного перезапуска. Длинный прогон минимум 30–60 минут с открытием меню/изменением размера окна; отдельные проверки сети и устройства вывода.

### B. Настольная библиотека и узнаваемый интерфейс

Ввести метаданные/обложки, фоновое сканирование папок, постоянные настройки и SQLite-репозиторий. Файловая идентичность и Unicode должны быть явными правилами; исчезнувший/перемещённый файл не должен ломать всю библиотеку. Не читать теги синхронно при отрисовке списка.

Параллельно реализовать дизайнерскую основу и основные UI-компоненты, чтобы не повторять технический вид 0.2.0. Добавить избранное, плейлисты и сохранение очереди/позиции после определения формата данных.

### C. Сетевой Zizi и соответствие мобильной версии

Перенести сетевые контракты, безопасную авторизацию установки, резолвер, кэш, загрузки, обработку квот и ошибок. Серверные ключи не должны попадать в публичные исходники, CLI-параметры FFmpeg или диагностические CSV. Для авторизованного потока потребуется отдельное безопасное решение транспорта; технический прямой URL-стенд его не заменяет.

Завести матрицу соответствия каждой функции/исправления Android конкретному desktop-аналогy и тесту. Не объявлять функциональный паритет только потому, что появились похожие кнопки.

### D. Доставка и Windows-интеграция

Стабилизировать CI, лицензии зависимостей, размещение FFmpeg, сохранение пользовательских данных, медиаклавиши/SMTC, трей и смену устройства. После определения канала распространения решить установщик, подпись и обновления. app-image, EXE-установщик и один переносимый EXE — разные требования.

## 11. Локальная сборка текущей версии

Версии: JDK 21, Gradle 8.11.1, Kotlin 2.1.0, Compose Multiplatform 1.7.3, kotlinx.coroutines-swing 1.9.0. FFmpeg внешний; конкретная версия установленного у пользователя бинарника в этой фиксации не сохранена.

Привычный вариант — распаковать Desktop рядом с рабочим Audio Lab:

````text
ZiziDesktop/
    ZiziAudioLab-0.1.0/
    ZiziDesktop-0.2.0-preview/
````

````powershell
cd .\ZiziDesktop-0.2.0-preview
.\Build-Desktop.cmd -FfmpegPath "C:\Tools\ffmpeg\bin\ffmpeg.exe"
````

При отдельной установке Gradle Audio Lab не нужен:

````powershell
.\Build-Desktop.cmd -GradleHome "C:\Tools\gradle-8.11.1" -FfmpegPath "C:\Tools\ffmpeg\bin\ffmpeg.exe"
.\Build-Desktop.cmd -Action package -GradleHome "C:\Tools\gradle-8.11.1" -FfmpegPath "C:\Tools\ffmpeg\bin\ffmpeg.exe"
````

Скрипт выполняет аудиотесты до запуска или упаковки. Результат EXE: `build/compose/binaries/main/app/ZiziDesktop/ZiziDesktop.exe`. Рядом обязательны остальные файлы app-image. FFmpeg не включён; в GUI его путь выбирается отдельно или задаётся FFMPEG_PATH.

Лог сборки: `logs/desktop-build.txt`. Диагностика аудио: `%LOCALAPPDATA%/ZiziDesktopPreview/logs`. Android SDK для этой настольной сборки не нужен.

## 12. Один репозиторий или два

**Рекомендация сейчас: один ZiziPlayer с раздельными каталогами, сборками и тегами.** Это сохраняет общую историю продукта и облегчает следующий перенос. Отдельное репо имеет смысл при независимых командах/правах, отдельном публичном продукте или самостоятельном релизном цикле, но само по себе не решает архитектуру и дублирование кода.

Рекомендуемая текущая структура без перестройки Android:

````text
ZiziPlayer/
    .github/workflows/build.yml        # только Android APK
    .github/workflows/desktop.yml      # отдельный ручной Windows CI
    ZiziPlayer-v6.39.9.zip              # мобильный ZIP пока в корне
    desktop/current.json               # точный исходник Desktop + SHA-256
    desktop/releases/ZiziDesktop-0.2.0-preview-source.zip
    docs/desktop/HANDOFF_DESKTOP_0.2.0.md
    docs/desktop/REPO_UPLOAD_GUIDE.md
    ci/extract_desktop.py
````

Версии не обязаны совпадать: Android 6.39.9 и Desktop 0.2.0-preview — разные стадии реализации одного продукта. Android tags: `v6.39.9`, `v6.40.0` и т.п.; Desktop tags: `desktop-v0.2.0-preview`. Для Desktop нельзя использовать просто `v0.2.0`: этот namespace принадлежит APK-сборкам.

Долгосрочно исходники лучше хранить распакованными: появятся нормальные diff/review, отдельные модули, менее хрупкие тесты и выбор версии. Но миграция всего мобильного репо не является условием публикации текущего десктопного ZIP.

## 13. Что обнаружено в существующем build.yml

Файл заново получен из GitHub 8 сентября 2026. Сейчас он запускается на каждый push в main/master, теги v* и любой published release. Поэтому загрузка одного .md уже способна запустить ненужную мобильную сборку.

При этом неверно говорить, что Desktop ZIP непременно будет собран как APK. Действующий selector читает корневые ZIP, ищет единственный settings.gradle.kts, затем app/build.gradle.kts с versionCode/versionName, выбирает максимальный versionCode. Наш GUI-архив не имеет Android app/build.gradle.kts, поэтому его нормальная версия будет пропущена. Повреждённый ZIP в корне всё же может оборвать просмотр архивов — лишние ZIP лучше не класть в корень.

**Более серьёзный риск — release:** workflow реагирует на любой published release и может прикрепить последний APK к desktop-релизу. Одних push.paths для защиты от этого недостаточно. Для tags path-фильтры не применяются, а release — отдельное событие.

Подготовленная версия build.yml добавляет path-фильтр для `ZiziPlayer-v*.zip` и самого Android workflow, Android tag pattern, пропуск desktop release на уровне job и валидацию релизного namespace. Поле ручного attach_to_tag не может использоваться для desktop-тега. Значения тегов передаются в shell через env, не подставляются как кусок кода.

Существующий selector, мобильные/серверные проверки, JDK 17 для Android, подпись, сборка APK и артефакты сохранены. Мобильные ZIP не перепаковывались; внутренние workflow этих ZIP сами по себе GitHub не запускает. Точный diff лежит рядом с этим handoff. Это предложенное изменение, не уже применённый commit.

## 14. Новый Desktop CI и границы подтверждения

`desktop.yml` запускается только через Actions → Run workflow. Он читает desktop/current.json, проверяет SHA-256, безопасно извлекает архив, ставит JDK 21/Gradle 8.11.1, устанавливает FFmpeg для интеграционных тестов, запускает Build-Desktop.ps1 с package и выгружает app-image/отчёты как Actions artifacts.

Desktop workflow имеет только contents:read, не использует Android signing/resolver secrets и ничего автоматически не публикует в Releases. FFmpeg не попадает в app-image. Для первого CI использован Chocolatey-пакет ffmpeg без фиксации версии — это явно воспроизводимостный долг; версия выводится в лог, после первого успешного CI её следует закрепить.

**GitHub Actions в этой работе не запускался.** Подтверждена локальная пользовательская Windows-сборка, но не работа нового Windows CI. Доступность Chocolatey-пакета, конкретный windows-latest image и первая упаковка на runner требуют отдельного прогона. GUI/звук на реальном устройстве нельзя проверить одним успешным headless CI.

## 15. Перед публикацией и продолжением

Сначала разместить обновлённый Android workflow на main; затем загружать handoff и desktop/releases ZIP. Если GitHub создаёт отдельные коммиты при загрузке через веб, такой порядок уменьшает лишние APK-сборки. Изменение самого build.yml намеренно запускает один Android-прогон — его результат полезно проверить.

Новый desktop release/tag создавать только после попадания защитного workflow в историю целевого коммита. Тег, указывающий на старый commit со старым workflow, не получает новую защиту автоматически. Desktop ZIP в ветке и source ZIP как Release asset — разные способы хранения: CI данного пакета читает именно файл из checkout.

Собранный EXE публиковать только вместе со всем app-image, в отдельном архиве Windows-бинарников. Не включать исходные пользовательские треки, логи с приватными путями/URL, .tools/.gradle, local-runtime файлы, ключи подписи или серверные токены. Проверить лицензии фактически распространяемых Java/Compose/FFmpeg компонентов.

Для следующего технического разбора нужны версия выбранного исходного ZIP, его SHA-256, последние build/test logs и чёткое различие между «реализовано», «подтверждено пользователем» и «проверено автоматическим тестом». Нельзя считать UI-паритет, серверную интеграцию или промышленную стабильность выполненными на основании текущего smoke-test.
