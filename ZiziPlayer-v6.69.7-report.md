## Что представляет собой проект

Android-приложение Kotlin/Jetpack Compose, minSdk 26, compileSdk/targetSdk 36.
Воспроизведение — Media3/ExoPlayer в PlaybackService, собственный DSP; локальная медиатека —
Room, MediaStore/SAF и MusicRepository. Есть сетевые каталоги/resolver, аккаунты,
синхронизация библиотеки, поиск текстов и отдельные Python-сервисы каталога, аккаунтов и текстов.
В репозитории мобильные исходники хранятся ZIP-архивами; Actions выбирает проект по максимальному
versionCode. Настольная ветка имеет отдельный workflow; в этой поставке она не изменена.

Текущая область UI — общая сворачиваемая шапка коллекций. Java CameraMorphGeometry задаёт
траекторию/материал; CollectionCoverMorph.kt рисует единственную обложку вне клиппинга списка,
системный контур камеры, соединение и локальную маску. BlurEffect работает на API 31+.
На API 26–30 остаётся предусмотренный исходной версией вариант без RenderEffect.

тест на API 35 успел пройти, поэтому вывод «любой blur гарантированно убивает эмулятор» неверен.

## Изменения 6.69.7

Главное изменение — уменьшение лишней нагрузки и диагностируемый, строгий CI.
Раньше оба запуска connectedDebugAndroidTest использовали `--rerun-tasks`: это принуждало
заново исполняться и зависимым задачам компиляции/упаковки при уже работающем эмуляторе.

Теперь debug APK и test APK собираются до запуска Android. Используется поддерживаемый
Gradle 8.11.1 task-specific `:app:connectedDebugAndroidTest --rerun`, без принудительной
пересборки всех зависимостей. Для этого запуска — максимум два Gradle worker и heap 1536 MiB.
Ограничение не меняет параметры обычной release-сборки.

Для каждого API задан собственный AVD, 2 ядра, 2048 MiB RAM, 256 MiB guest heap,
запрет snapshot. CI сохраняет SwiftShader GLES и отключает Vulkan feature эмулятора.
Это ограничение поверхности нестабильности CI, а не доказанное исправление графического
сбоя. RenderEffect в приложении и Android blur-тест НЕ выключены; KVM остаётся включённым.

`tools/run_camera_ci.sh` проверяет SDK/загрузку устройства, очищает прежние connected-результаты,
сохраняет stdout/stderr Gradle, непрерывный logcat, timeline памяти хоста/процессов,
ADB до/после, доступные сведения о графике и kernel tail. Отсутствие доступа к dmesg явно
попадёт в файл; оно не превращается в утверждение об OOM. Диагностика best-effort:
её сбой не маскирует исходный код ошибки Gradle. Автоматических повторов и continue-on-error нет.
Если сам эмулятор не загрузится до входа в скрипт, диагностика скрипта не появится;
тогда нужны логи Actions emulator-runner.

`tools/verify_camera_results.py` сверяет точные наборы тестов: 25 для API 28, 27 для API 35.
Пропуск, failure/error, пустой failure, дубликат, лишний/отсутствующий тест, битый XML или
непустой system-err блокируют выпуск. Это дополнительная проверка, а не замена exit status Gradle.
При добавлении тестов inventory нужно обновлять вместе с исходниками; это проверяет selftest.

В Android material harness добавлены только Log.i-маркеры перед изменением progress,
после idle и после PixelCopy. Assertions, допуски, test fixtures и SDK gates сохранены.
Error summary теперь видит camera-логи и неполные результаты. Диагностика прикладывается
к соответствующему camera artifact. Лог предварительной упаковки APK сохраняется отдельно.

## Установка в репозиторий

1. Загрузить `ZiziPlayer-v6.69.7.zip` в корень main **не распаковывая**.
2. Заменить корневой `.github/workflows/build.yml` файлом `build.yml` из этой поставки
   либо файлом `repo-update/.github/workflows/build.yml` внутри нового ZIP.
   Workflow внутри мобильного ZIP сам по себе GitHub не исполняет.
3. Лучше внести оба файла одним коммитом. Через телефон допустимо сначала загрузить ZIP,
   затем заменить корневой workflow: второй push запустит исправленный CI; первый запуск
   ещё использует старый сценарий. Не загружать workflow отдельно раньше нового ZIP:
   старые исходники не содержат нового tools/run_camera_ci.sh.
4. Дождаться JVM, API 28 и API 35, затем release/signature. Подписанный APK устанавливать
   поверх текущего с прежним ключом без очистки данных. Не оставлять другой ZIP с code 132.

При новом сбое нужны свежий camera artifact и полный лог Actions. В archive смотреть
`build/ci/android-api-35/gradle.log`, `completeness.json`, `logcat-full.txt`,
`host-timeline.txt`, `kernel-tail.txt` и `exit-code.txt`. Последний CameraMaterialCI marker
разделяет проблемы изменения состояния, ожидания idle и захвата кадра; отсутствие marker
само по себе не доказывает сбой конкретной операции.

Коммиты, запуски Actions, релизы и настройки GitHub в этой работе не изменялись.
