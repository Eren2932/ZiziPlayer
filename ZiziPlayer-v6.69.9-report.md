## Что действительно упало

В предоставленных логах компиляция Kotlin, Android test sources и JVM-тесты завершились
`BUILD SUCCESSFUL`. На API 28 выполнены 26 Android-тестов, один упал:

`CameraMorph6692UiTest.cameraDropPrecedesConnection6699`

Сообщение: `java.lang.AssertionError: The drop is rooted in the camera`.
API 35 и последующая release-сборка этим запуском не подтверждены. Предупреждения
эмулятора и ожидаемые ошибки негативных серверных фикстур не являются этим assertion.

Лог эмулятора указывает skin 320x640. В тесте бралась округлённая координата середины
между нижним краем камеры и кончиком капли, после чего от всего пикселя требовалась
почти полная чернота. Но пиксель — площадь, а не математическая точка.

Для production-геометрии на тестовой конфигурации 320x640, density=1, status=24:
при progress=0.31 и u=3.593449 кончик капли находится на y=20.871418,
а старый тест выбирает пиксель (160,20), занимающий y=[20,21]. Он пересекает границу.
Независимый Java2D-рендер даёт red=0.03529412 при пороге <0.03: старое утверждение
падает даже при правильно нарисованном контуре. Это воспроизведение дефекта пробы,
**не запуск Android/Skia**; точный цвет упавшего Android-пикселя исходный лог не сохранил.

Теперь тест выбирает пробу по самой геометрии Path.op, до чтения скриншота:
весь пиксель и дополнительный запас 0.5px должны лежать внутри капли. Проба находится
полностью ниже исходного круга камеры, поэтому одна статичная точка не может выдать
себя за растущую каплю. Проба зазора должна целиком лежать вне обоих контуров.

Для малых плотностей поиск охватывает u=3.10..3.65 вместо 3.35..3.65: это по-прежнему
строго раздельная фаза (касание при u=3.07), а запас до обоих контуров проверяется отдельно.
Пороги цвета не увеличены; чернота и обратный ход теперь проверяются по всем RGB-каналам.
Нет подбора проходящего цвета, sleep/retry, отключения тестов или continue-on-error.
На вышеуказанной конфигурации новая проба капли — (160,19), зазора — (160,27).

## Убрана точка после завершения захвата

Ранее anchorAlpha возрастала до 1 и оставалась такой при progress=1: overlay продолжал
рисовать чёрный контур после исчезновения обложки. Это было частью прежнего контракта;
старые endpoint-тесты требовали точку. По новому требованию контракт изменён.

Введено затухание только в последней десятой части захвата:

    q = clamp((progress - 0.90) / 0.10, 0, 1)
    S(q) = 6*q^5 - 15*q^4 + 10*q^3
    anchorAlpha = smooth(progress / 0.18) * (1 - S(q))

При отсутствии target alpha по-прежнему 0. У S нулевые первая и вторая производные
на концах: нет скачка прозрачности, скорости или ускорения затухания. На основном
этапе контакта камера сохраняет прежнюю непрозрачность. В конце:

| Progress | Anchor alpha, приблизительно |
| --- | --- |
| 0.90 | 1.000000 |
| 0.925 | 0.896484 |
| 0.95 | 0.500000 |
| 0.975 | 0.103516 |
| 1.00 и overscroll | **0 точно** |

При полном завершении imageAlpha тоже равна 0, goo отсутствует, команда рисования
контура не выполняется. Нет дополнительного таймера, нового состояния или задержки:
прямой/обратный скролл использует одну функцию. Координаты, формы капли и соединения,
траектория, safety clip, blur и источник обложки сохранены.

Исчезает именно **нарисованный приложением** контур. Физический вырез камеры экрана
приложение скрыть не может. Явно включённая служебная диагностическая обводка — отдельный
debug-режим, не обычное отображение.

- Production Java: конечный alpha=0, overscroll, монотонное плавное исчезновение,
  видимость при контакте и обратимость. Мутации «вечная точка», «всегда невидимая камера»

точки для центральной/боковой камеры и весь прямоугольник вокруг центрального контура
с запасом под расширение на progress=1 и 1.2. Проверяются обратный ход, прежняя капля,
яркость и blur. Два теста переименованы под новый конечный контракт, явный inventory
синхронизирован: API 28 — 26 тестов, API 35 — 28 тестов. Проверка полноты не ослаблена.

В the Computer отсутствуют Gradle, Android SDK и эмулятор. Полная Kotlin/Compose-компиляция,
Android Path.op/PixelCopy, API 28/35, release/R8, подпись APK и реальное устройство
**не проверены для исправленного пакета**. Статические Kotlin-проверки — эвристики,
не замена компилятору; Java2D — не замена Skia. До зелёного Actions пакет является
проверенным офлайн кандидатом, а не подтверждённой Android-сборкой.

## Как применить

1. **Заменить существующий `ZiziPlayer-v6.69.9.zip` в корне GitHub этим файлом под тем же именем.**
   Версия 6.69.9 и code 134 сохранены по условию работы. Не добавлять второй ZIP с code 134
   под другим именем: распаковщик корректно отклонит две максимальные версии.
2. `.github/workflows/build.yml` менять не нужно. Push замены ZIP запускает имеющийся workflow.
3. Дождаться нового запуска: JVM/компиляция → API 28 **26/26** → API 35 **28/28** → release/APK.
   Старый зелёный запуск не подтверждает новые байты архива.
4. Установить APK с прежней подписью поверх приложения, без очистки данных.
   На телефоне проверить медленное завершение захвата, остановку в полном состоянии,
   глубокий скролл и обратный ход. Нарисованная точка не должна оставаться; физическая камера останется.

Если CI снова упадёт, нужен новый полный лог и артефакт camera-collection-api-28 либо -35.
Сообщение теста теперь включает progress, u, размер изображения, координаты и фактический цвет.
