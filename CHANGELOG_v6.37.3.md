# ZiziPlayer 6.37.3 — ключ на устройство вместо вечного токена в APK

versionCode 70 · targetSdk 36 · zizi_catalog 1.8 · zizi_guard 1.8 · zizi_resolver 1.6.2

Закрывает пункт 4.2 внешнего ревью 6.37.0 (ступени 2 и 3), пункт 4.3 (алерт) и пункт Б
(targetSdk). Плюс восстанавливает монтирование каталога, потерянное при выкатке 6.37.2.

## Зачем

`RESOLVER_TOKEN` запечён в релиз и достаётся из APK за минуту. Ротация не лечит: новый токен
уедет в новый APK. В 6.37.2 появилась ступень 1 — квота по IP и три независимых класса нагрузки.
Ступень 2 («квота на устройство») была написана в `zizi_guard.py` и **не исполнялась ни разу**:
она опирается на заголовок `X-Zizi-Install`, а в клиенте не было ни одного упоминания installId
(`grep -rc installId app/src` -> 0). Это тот же класс дефекта, что 404 на `/catalog/health`:
код есть, подключения нет.

## Что изменилось

### Клиент

- **новый** `app/src/main/java/app/ziziplayer/data/remote/ZiziInstall.kt`
  `installId` — случайный UUID в своих SharedPreferences: живёт через обновления, умирает при
  переустановке. Ни ANDROID_ID, ни рекламного идентификатора: это единица учёта и отзыва, а не
  личность. Здесь же обмен бутстрап-токена на короткоживущий ключ и его кэш на диске.
  SharedPreferences, а не DataStore, потому что `authHeaders()` — обычная функция в пути каждого
  запроса, и корутина там означала бы либо блокировку потока, либо переписывание всего слоя.
- `ZiziResolve.authHeaders()` — одна точка на всё приложение: отдаёт ключ устройства, если он
  выпущен, иначе токен сборки; `X-Zizi-Install` уходит **всегда**, даже без токена.
- `ZiziResolve.imageUrl()` — `&i=<installId>` параметром: обложки грузит картиночный загрузчик,
  он ходит по строке адреса и заголовков не ставит. Без этого залп из 100 обложек считался бы
  анонимным трафиком с IP.
- `ZiziApplication` — `ZiziInstall.ensure()` до первого сетевого запроса.
- `app/build.gradle.kts` — compileSdk/targetSdk 36 (Play не принимает ниже 36 с 31.08.2026),
  versionCode 70, versionName 6.37.3.

### Сервер

- `zizi_guard.py` 1.8 — выдача и проверка ключей (hmac-sha256, формат `zd1.<payload>.<sig>`),
  режимы `ZIZI_DEVICE_MODE=off|warn|require`, отзыв по `ZIZI_DEVICE_DENY`, класс квоты `auth`
  (5/12 и 3/6 — самый узкий в файле), счётчики `device`, `device_pct`, `rejected_403`.
  Личность в квоте берётся **из подписи**, а не из заголовка: подделать installId теперь
  означает подделать подпись.
- `zizi_catalog.py` 1.8 — роут `GET /auth/device`, закрытый бутстрап-токеном в любом режиме
  (`TOKEN_REQUIRED`); валидация installId по длине и алфавиту, чтобы чужой клиент не раздувал
  память ключами квоты. installId для `/img` читается и из параметра `i`.
- `zizi_resolver.py` 1.6.2 — `_check_token` принимает ключи устройств; в `require` бутстрап-токен
  больше не пропуск на `/resolve` и `/stream`. **Врезка `include_router(catalog_router)` теперь
  лежит в репозитории**, а не добавляется руками на VPS.
- **новый** `server/tools/test_zizi_device.py` — 46 утверждений, проверены пятью мутациями
  (снят срок, снята сверка подписи, отключён отзыв, личность из заголовка, открытая выдача) —
  обнаружены все пять.
- **новый** `server/deploy-catalog-1.8.sh` — валится до рестарта, если во **привезённом**
  резолвере нет врезки, если тесты не прошли на этой машине, если после рестарта
  `/catalog/health` не 200, если версия каталога не 1.8 или если `/auth/device` пускают без
  токена. В 1.7 всё это было предупреждениями в середине вывода — и одно из них мы пропустили.
- **новый** `zizi-watch.sh` — крон раз в 10 минут: жив ли сервис, смонтирован ли каталог, что
  YouTube думает о стране выхода, не выросла ли доля отказов. Пишет в Telegram на смене
  состояния, а не каждые 10 минут.
- `.github/workflows/build.yml` — +2 шага, и снят `|| true` с проверки аргументов вызовов:
  она теперь чистая (0 подозрений), незачем держать её декоративной.

## Найдено по пути

`hmac.compare_digest` на строке с не-ASCII символами бросает `TypeError`. То есть один запрос с
заголовком `Authorization: Bearer привет` возвращал **500 с трассировкой в лог**, а не 401 — и
так было во всех выкаченных версиях резолвера. Сравнение секретов переведено на байты
(`_same`), тест на мусор в заголовке добавлен.

## Приёмка

```
самотест проверок      8 фикстур · провалов 0
синтаксис Kotlin       0 · импорты 0 · статические ссылки 0 · аргументы вызовов 0
синтаксис сервера      15 файлов · 0
тесты границы          73 утверждения · провалов 0
ключ на устройство     46 утверждений · провалов 0 · мутаций пропущено 0
врезка в zizi_catalog   17 утверждений · провалов 0
скан на секреты        чисто
```

Оговорка не смягчается: Kotlin здесь **прошёл проверки, а не собрался** — компилятора у меня
нет. Сервер, наоборот, запускался по-настоящему: `fastapi` подменён заглушкой, а `zizi_guard` и
`zizi_catalog` импортируются и исполняются в тестах.

## Развёртывание

Порядок важен: сначала сервер в режимах по умолчанию (`warn`), потом APK. Наоборот — тоже
безопасно, но тогда клиент сутки ходит с бутстрап-токеном.

```
scp server/zizi_catalog.py server/zizi_guard.py server/zizi_resolver.py root@VPS:/opt/zizi/
scp -r server/tools root@VPS:/opt/zizi/
scp server/deploy-catalog-1.8.sh zizi-watch.sh root@VPS:/opt/zizi/
ssh root@VPS 'cd /opt/zizi && bash deploy-catalog-1.8.sh ./zizi_catalog.py'
ssh root@VPS 'echo "ZIZI_DEVICE_KEY=$(openssl rand -hex 32)" >> /opt/zizi/zizi.env && systemctl restart zizi-resolver'
```

По умолчанию `ZIZI_DEVICE_MODE=warn`: старый APK продолжает работать без изменений, ключи уже
выдаются и считаются. Переключение — по цифрам, не на глаз:

- `guard.anon_pct` -> 0 — можно `ZIZI_CATALOG_TOKEN_MODE=require`;
- `guard.device_pct` -> 100 — можно `ZIZI_DEVICE_MODE=require`. После этого токен, вшитый в
  каждый из 30+ выпущенных релизов, годится ровно на одно: попросить себе ключ, упираясь в
  самую узкую квоту сервера, и быть отозванным одной строкой в `zizi.env`.
