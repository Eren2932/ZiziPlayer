## 1. Что это за проект, в трёх абзацах

Android-плеер на Compose + Media3. 67 файлов Kotlin, 28 011 строк. `minSdk 26`,
`compileSdk 36`, `targetSdk 36`, `versionCode 70`, `versionName 6.37.3`. Room версии схемы **9**,
`exportSchema = true`. Свой DSP (27 пресетов, биквады, спектр) — то, чего у эталона нет вовсе.

Звук приходит **не** из каталога, который человек видит. Витрина — Deezer (названия, артисты,
альбомы, обложки высокого разрешения, **ISRC**). Звук — YouTube через собственный резолвер
`ZiziResolve` на VPS (`yt-dlp`, узел в обход гео-блока). Стык между этими мирами — один
серверный вызов `/match/deezer`: по id Deezer сервер находит ту же запись на YouTube и
возвращает `videoId`, кладя `isrc → videoId` в SQLite навсегда.

Сервер: Timeweb, Ubuntu 22.04, **1 ядро / 890 МБ RAM**, IPv4 `147.45.166.244`, `uvicorn
--workers 1`, nginx перед сервисом **нет**. Это не мелочь: на одном ядре любой фанаут `yt-dlp`
съедает машину, и половина серверных решений в проекте объясняется именно этой цифрой.

## 2. Архитектура, которую нельзя ломать

```
Compose UI ──► MainViewModel ──► MusicRepository ──► CatalogRegistry
                                                      ├── MixCatalog (id "mix") ─┬── DeezerCatalog "dz"
                                                      │                          ├── InnertubeCatalog "yt"
                                                      │                          └── AudiusCatalog "audius"
                                                      └── (локальная медиатека — Room, MusicScanner)

Media3 loading thread ──► RemoteCatalog.resolveStream ──► /match/deezer ──► /resolve ──► CDN
```

**Инварианты. Нарушение любого из них ломало проект как минимум один раз:**

1. **Id трека — `r:<провайдер>:<remoteId>`**, для микса `r:mix:dz:3135556`. На этой строке стоят
   избранное, плейлисты и офлайн. Менять формат нельзя никогда: в чужих базах лежат старые id.
2. **`resolveStream` вызывается в момент открытия потока, а не заранее.** Именно поэтому истекающие
   ссылки CDN здесь не проблема. Не «оптимизировать» это кэшированием url.
3. **Сопоставление живёт на сервере.** На телефоне это батарея и секунды задержки у каждого; на
   сервере — один раз для всех.
4. **`include_router(catalog_router)` лежит в `server/zizi_resolver.py` в репозитории** (строка
   1749). До 6.37.3 он дописывался руками на VPS, и штатный `scp` его снёс — каталог отдавал 404
   при `Application startup complete` без единой ошибки. Не выносить обратно в ручной шаг.
5. **`UNAVAILABLE` обрывает перебор каталогов, `OFFLINE` — нет** (`RemoteCatalog.kt`,
   `withFallback`). Записи нет — у соседа её тоже нет; этот не ответил — сосед ответит.
6. **Пользователь не знает слов «Deezer», «Innertube», «Audius».** Наружу все каталоги
   называются «Музыка». Не выводить источник в UI как выбор.

## 3. Состояние безопасности (закрыто в 6.37.2–6.37.3, не переделывать)

Токен в APK больше не пропуск, а **бутстрап**. Схема: `installId` (UUID в DataStore,
`ZiziInstall.kt`) → `GET /auth/device` с бутстрап-токеном → короткоживущий ключ HMAC-SHA256,
`installId` **внутри подписи**, сутки жизни, отзыв строкой `ZIZI_DEVICE_DENY` в `zizi.env`
**без выпуска APK**.

Квоты — три независимых класса (`img` / `catalog` / `match`), плюс `auth` самым узким. Разделение
не косметика: залп из 100 обложек на плейлист физически не может исчерпать квоту сопоставления.
Глобальный потолок процессов `ZIZI_CATALOG_SLOTS` (**не** `ZIZI_EXTRACT_SLOTS` — то занято
резолвером и равно 1). `ExtractBusy` → **429 + Retry-After**, и в кэш промахов не пишется
ничего: иначе отказ «нет слота» превратился бы в вечное «трека не существует» на 6 часов.

`/flush` — на отдельном `ZIZI_ADMIN_TOKEN`.

**Переключение режимов только по цифрам из `/catalog/health`, не на глаз:**
`guard.anon_pct == 0` → можно `ZIZI_CATALOG_TOKEN_MODE=require`;
`guard.device_pct == 100` → можно `ZIZI_DEVICE_MODE=require`. После второго все 30+ выпущенных
релизов становятся безвредны сами. По умолчанию оба режима — `warn`.

Ключевые переменные `zizi.env`: `ZIZI_TOKEN`, `ZIZI_ADMIN_TOKEN`, `ZIZI_DEVICE_KEY`,
`ZIZI_DEVICE_MODE`, `ZIZI_DEVICE_TTL`, `ZIZI_DEVICE_DENY`, `ZIZI_CATALOG_TOKEN_MODE`,
`ZIZI_CATALOG_SLOTS`, `ZIZI_CATALOG_SLOT_WAIT`, `ZIZI_MISS_TTL`, `ZIZI_TG_TOKEN`, `ZIZI_TG_CHAT`,
`ZIZI_SP_ID`/`ZIZI_SP_SECRET` (Spotify-путь в каталоге опционален и по умолчанию выключен).

Выкатка: `deploy-catalog-1.8.sh` — **валится до рестарта** на отсутствии врезки, на упавших
тестах, на `/catalog/health != 200`, на версии не 1.8 и на открытом `/auth/device`.
Мониторинг: `zizi-watch.sh` в кроне раз в 10 минут, Telegram **только на смене состояния**.

## 4. Диагноз двух жалоб, с которыми пришёл заказчик

### 4.1 «Нет отметок 2026, свежего нет»

Причина не в гибриде, а в одном вызове. `server/zizi_catalog.py:494`:

```python
j = dz_get("chart", limit=limit)
```

Витрина стоит на **глобальном чарте Deezer, и только на нём**. Глобальный чарт — это
усреднённая мировая поп-музыка с сильным перекосом во французский рынок (Deezer — французский
сервис). Новинок там по определению почти нет: чарт инерционен.

Не используется ничего из того, что делает витрину живой: `editorial/{country}/releases`
(новые релизы), `chart/{genre_id}` (чарты по жанрам), `editorial/{country}/charts`,
`genre` (жанровые полки), `radio` (готовые радиостанции Deezer), локаль/страна вообще нигде
не передаётся. Раздел «Артисты» на главной берётся из того же чарта, а страница артиста
(`/catalog/artist`) отдаёт **только топ-треки** — без альбомов, без синглов, без «похожих».

Лечится сервером, без релиза APK. Подробности — раздел 5.1.

### 4.2 «Некоторые песни ушли»

Это правда, и механизм точный. Путь воспроизведения теперь такой:

```
тап → /match/deezer?id=... → match_track() → _hunt() → score() → best_s >= WEAK ?
        нет → miss_put(key, "no confident match") → HTTP 404 → UNAVAILABLE → трек пропускается
```

`zizi_catalog.py:402-403`: `CONFIDENT = 20.0`, `WEAK = -5.0`. `MISS_TTL = 21600` — **отрицательный
ответ живёт 6 часов**, то есть один неудачный поиск гасит трек на полдня.

Отсюда три разных причины исчезновения, и путать их нельзя:

1. **Записи нет в Deezer.** Фонк-эдиты, ускоренные версии, «MONTAGEM …», бразильский фанк,
   SoundCloud-релизы — их в лицензионном каталоге не существует. Раньше такой трек находился
   сырым поиском YouTube, потому что там он лежит как видео. Теперь витрина о нём не знает,
   и он не появляется в выдаче вовсе.
2. **Запись в Deezer есть, а на YouTube официальной нет** — или лежит под названием, которое
   `score()` не связывает с оригиналом. Трек виден в списке, но при тапе пропускается.
3. **`InnertubeCatalog` не опрашивается без VPN** (сознательно, 6.36.0: он не отказывает, а
   висит 4.5 секунды на каждый поиск). То есть второе плечо, которое раньше и приносило этот
   слой музыки, сейчас просто выключено у большинства.

Важно понимать: `MixCatalog` **уже** умеет объединять источники и схлопывать дубликаты по
нормализованным артисту, названию и длительности с точностью до 5 секунд, причём побеждает
версия с обложкой. То есть «не потеряв ничего» — это не переписывание архитектуры, а
включение второго плеча и один новый серверный резерв. Раздел 5.2.

## 5. План 6.38+ по приоритету. Это и есть работа

### 5.1 Свежесть и глубина витрины — сервер, без релиза APK

Новые эндпоинты в `zizi_catalog.py` (все на Deezer, все без ключей):

| Роут | Deezer | Зачем |
|---|---|---|
| `/catalog/releases?cc=RU&limit=` | `editorial/{cc}/releases` | полка «Новинки» — прямой ответ на «нет 2026» |
| `/catalog/genres` + `/catalog/chart?genre=` | `genre`, `chart/{id}` | жанровые полки вместо одного мирового чарта |
| `/catalog/artist/full?id=` | `artist/{id}`, `/top`, `/albums`, `/related` | страница артиста как у эталона: шапка, топ, дискография, похожие |
| `/catalog/album/list?artist=` | `artist/{id}/albums` | альбомы и синглы с датами — «2026» становится видимым |
| `/catalog/radio?artist=` | `artist/{id}/radio` | готовый плейлист-радио одним вызовом |
| `/catalog/search?type=artist\|album\|playlist` | `search/artist`, `search/album` | сейчас поиск умеет только треки |

Кэш обязателен: `editorial` и `chart` — в SQLite на 6–12 часов. Одно ядро, 890 МБ.

### 5.2 Ничего не терять — два плеча вместо одного

1. **Резерв сопоставления на стороне сервера.** Если Deezer не знает записи, а человек её ищет —
   отдавать результат сырого поиска YouTube как трек витрины с обложкой из `/img`. Новый роут
   `/catalog/search?src=mix` со склейкой на сервере: телефон получает один список и не платит
   4.5 секунды за висящий Innertube.
2. **`miss_put` перевести с 6 часов на 30–60 минут и различать причины.** «Нет в Deezer» и
   «не нашлось на YouTube» — разные диагнозы, а живут одинаково.
3. **Порог `WEAK = -5.0` пересмотреть на замере**, а не на глаз: снять 100 треков, посчитать
   долю пропусков, только потом двигать. Иначе слабое сопоставление начнёт подсовывать не тот трек,
   а это хуже отсутствия.
4. **Показывать, что трек не сопоставлен, до тапа**, а не пропускать молча. Серая строка
   «недоступно» честнее, чем плеер, который сам листает дальше.

### 5.3 Экраны: страница артиста и новый плейлист

Сейчас `RemoteCatalog.collection()` возвращает **плоский список треков** для альбома, плейлиста
и артиста одинаково. Экран артиста как таковой отсутствует — это и есть главный разрыв с
эталонным скриншотом.

Что делать в клиенте (требует твоей сборки):
- новый экран `CollectionScreen`: большая обложка-шапка, градиент из палитры обложки, крупный
  заголовок, автор/число сохранений/длительность, кнопки «играть», «перемешать», «скачать»,
  «сохранить», липкая панель при скролле;
- экран артиста: шапка с фото, «Популярные треки» (5 + «ещё»), «Дискография» плитками с годами,
  «Похожие артисты» (`/catalog/similar` уже готов и не используется клиентом);
- `Sheets.kt` — 131 КБ, `LibraryScreen.kt` — 116 КБ. Новые экраны **отдельными файлами**,
  не дописывать в эти.

### 5.4 Радио по треку и «похожие» — то, что сдвинет отметку

`/catalog/similar` (похожие артисты) на сервере **уже есть и клиентом не вызывается ни разу**.
Плюс `artist/{id}/radio`. Сложить это с собственной историей прослушиваний из Room — и получается
первый настоящий шаг от плеера к сервису. Ни лицензий, ни аккаунтов не требует.

Это единственный пункт, который двигает оценку продукта. Всё остальное в списке — гигиена.

### 5.5 Долги, которые никуда не делись

1. **`app/schemas/**` отсутствует** при `exportSchema = true`. Единственный риск потери **чужих**
   данных. Генерирует `ksp` — только сборкой заказчика. Плюс шаг CI «схема версии 9 существует».
2. **Репозиторий — зип в корне, диффов нет.** На этом держится весь класс багов 6.30–6.37.
3. **Строка «кто ответил»** (`mix · dz · 380 мс · catalog 1.8`) — полдня работы, ловит 90%
   болезни «написано, но не подключено».
4. **Smoke-тест на состав `CatalogRegistry`** — ломалось семь релизов подряд, теста нет.
5. **AAB вместо APK**, политика приватности, Data Safety — если магазин вообще цель.
6. **Клиент: 3 unit-теста на 28 000 строк**, инструментальных нет.

## 7. Как со мной работать, чтобы не потерять время

1. **Kotlin я не компилирую.** Компилятора нет. Проверяю синтаксис, импорты, статические ссылки
   и аргументы вызовов эвристиками — это ловит много, но говорит «прошёл проверки», а не
   «собрался». Компилирует только твой CI. Серверный Python я исполняю по-настоящему
   (`fastapi` подменён заглушкой в `server/tools/_stub/`).
2. **Патч-архивы не заливать в корень репы как релиз.** Сборка №336 умерла именно на этом.
   Отдавать всегда полный зип с `settings.gradle.kts` в корне архива. Шаг `Unpack source zip`
   с 6.37.3 такие архивы пропускает с предупреждением, но мусорить незачем.
3. **Порядок выкатки: сервер, потом APK.** Оба новых режима по умолчанию `warn`, старые сборки
   продолжают работать.
4. **Проверка без `exit 1` — это комментарий, а не проверка.** Один такой `echo` в
   `deploy-catalog-1.7.sh` стоил нам каталога в 404 на сутки.
5. **Диалоги обрываются на кредитах.** Отсюда этот файл. Если работа большая — сначала
   короткий план в сообщении, потом код: план переживёт обрыв, полусобранный зип нет.
