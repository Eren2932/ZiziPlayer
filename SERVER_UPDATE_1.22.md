# Серверное обновление 1.22 (Reco 2.5-prefetch-rc1)

Цель: главная и подборка для **известных** артистов отдаются из кэша, без обращений к Deezer. Холодный путь не стал быстрее: это потолок бакета 8/с, а не код.
Клиент менять не нужно: схемы ответов те же.

Статус: все наборы тестов зелёные в песочнице на фикстурах (включая 26 новых в `test_prefetch122.py`). **На живом Deezer и на VPS не проверялось.** Цифры ниже, модель.

## Что меняется на VPS

Из рабочих файлов меняется **один**: `zizi_reco.py` (2.4-speed-rc1 → 2.5-prefetch-rc1). `zizi_catalog.py` и `zizi_browse.py` остаются от 1.21, поэтому `/catalog/health` по-прежнему покажет `1.21-speed-rc1`. Новая версия видна в `/reco/health` (`2.5-prefetch-rc1`).

Остальное только в `tools/`: `test_prefetch122.py` (новый), `test_zizi_reco.py` (список маршрутов теперь с `/reco/prime`), `deploy_server.py` (новый тест в предустановочной проверке), `server_known.json`, `server_bundle_seal.json`, `bench_home.py`.

## Что делает 2.5

1. **SWR-кэш.** Протухший, но не пустой ответ отдаётся сразу, а обновляется один раз в фоне. Окна после TTL: граф похожих до 6 суток, альбомы 18 ч, радио 21 ч, треки альбомов 5 суток. Пустой ответ радио (Deezer иногда его отдаёт) не затирает хорошие данные: старое остаётся, повтор через 10 минут.
2. **Горячий набор.** В SQLite (`reco_hot`, `reco_warm` в `catalog.db`) лежат только id артистов, счётчики и время прогрева. Пользователей и истории прослушиваний там нет. Источники: тапы по артистам (`/reco/onboard?a=ID`), завершённые подборки, прежняя статистика совместных выборов (`reco_single`, `reco_pair`), колода онбординга, ближайшие соседи.
3. **Фоновый префетч.**
   - Стартует через 45 с после запуска сервера.
   - Не работает, пока недавно был живой запрос или в бакете меньше 6 токенов из 8: люди важнее.
   - Потолок 2400 вызовов в час. Если Deezer не отвечает, пауза 5 минут.
   - Размер набора 300 артистов, первые 120 по числу выборов. Предсборка пула страницы артиста только для первых 30.
4. **Трассировка.** `/reco/health` показывает `prefetch`, `home.served` и `home.trace` (время, число вызовов, hits по последним 10 сборкам).
5. **`GET /reco/prime?a=id1,id2`.** Подсадить артистов в набор вручную (до 30 id). Необязателен: набор сам берёт `reco_single`.
6. **Выключатели без деплоя.** `ZIZI_PREFETCH=0` отключает фоновый префетч, `ZIZI_SWR=0` отключает SWR. Переменные в окружении юнита systemd, потом `systemctl restart`.

## Модельные цифры

`python3 tools/bench_home.py <задержка_Deezer_с> <alive|dead> <секунд_на_выбор>` (из каталога `server/`). Фейковый Deezer, 7 артистов, реальный бакет 8/с.

| Состояние | `/reco/home` | Вызовов к Deezer |
|---|---|---|
| Холодно, Deezer 0.2 с | 3.3–3.7 с | 32–36 |
| Прогрев при тапах (выбор 8 с) | 0.8 с | 12 |
| Все сиды в горячем наборе и прогреты | 0.02 с | 0 |

Полный прогрев 300 артистов стоит ~4800 вызовов. При потолке 2400/ч это около 2 часов. За это время набор добирается постепенно, первыми идут самые выбираемые.

## Установка

```bash
# 1. Проверка. Ничего не пишет.
/opt/zizi/venv/bin/python ~/zizi-1.22/server/tools/deploy_server.py --check
# ждём: zizi_reco.py replace (база 2.4-speed-rc1), остальные skip

# 2. Бэкап базы (WAL: копировать .db на ходу нельзя).
sqlite3 "$ZIZI_CATALOG_DB" ".backup '/opt/zizi/catalog.before-1.22.db'"

# 3. Установка (откат автоматический, если health не сошёлся).
sudo /opt/zizi/venv/bin/python ~/zizi-1.22/server/tools/deploy_server.py --apply

# Ручной откат
sudo /opt/zizi/venv/bin/python ~/zizi-1.22/server/tools/deploy_server.py --rollback /opt/zizi/server-backups/<папка>
```

Установщик принимает базы 1.19, 1.20 и 1.21. Две новые таблицы создаются при первом старте, существующие не трогаются, откат на 2.4 их игнорирует.

## Топ-5 ваших артистов из локальной базы

Пользователей в базе нет: набор общий для сервера. Если приложением пользуетесь вы, это ваши выборы.

```bash
DB=${ZIZI_CATALOG_DB:-/opt/zizi/catalog.db}
sqlite3 -header -column "$DB" "SELECT a AS artist_id, n FROM reco_single ORDER BY n DESC LIMIT 5;"
```

После установки то же самое про `reco_hot` (наполняется тапами и завершёнными подборками):

```bash
sqlite3 -header -column "$DB" "SELECT a AS artist_id, n FROM reco_hot ORDER BY n DESC LIMIT 5;"
```

Имена (необязательно, Deezer публичный):

```bash
for id in $(sqlite3 "$DB" "SELECT a FROM reco_single ORDER BY n DESC LIMIT 5;"); do
  echo "$id $(curl -s https://api.deezer.com/artist/$id | jq -r .name)"
done
```

Подсадить, если нужно (id через запятую):

```bash
H="Authorization: Bearer $T"; B=https://<ваш-хост>
curl -s -H "$H" "$B/reco/prime?a=111,222,333"
```

## Проверка после установки

```bash
H="Authorization: Bearer $T"; B=https://<ваш-хост>
curl -s -H "$H" $B/reco/health | jq '{version, warmed, warming, prefetch, upstream}'   # "2.5-prefetch-rc1"
curl -s -H "$H" $B/reco/health | jq '.home'      # served и trace последних сборок
```

Через 10–20 минут после установки и нескольких выборов артистов нужны: `/reco/health` целиком и `journalctl -u zizi-resolver --since "-30min" | tail -100`.
Главное в выводе: `prefetch` (шагов сделано, вызовов в час, пауза), `home.trace` (время сборки и hits против calls), `upstream.failures`.

## Риски

- Выигрыш получают только артисты из горячего набора. Новые, редкие и найденные поиском идут по прежнему холодному пути (3–5 с в модели, с частичным ответом и опросом клиентом).
- Префетч тратит до ~0.7 вызова/с в среднем из общей квоты Deezer. Если по `upstream.failures` или `bucket` видно давление, поставьте `ZIZI_PREFETCH=0`.
- Прогрев страницы артиста в префетче работает по возможности.
- RAM: набор 300 артистов и SWR-очередь (до 128 задач) на 890 МБ укладываются. Нагрузочный прогон на реальном SQLite (12 потоков, SWR и префетч вместе) прошёл без ошибок. Это не замена наблюдению за `free -m` первые сутки.
- `test_probe_contention` нестабилен по времени (раньше падал на исходном коде, сейчас зелёный).
