# Zizi Player 6.7.0 (versionCode 16)

База — 6.6.1. Тема обновления: **библиотека перестаёт быть слепой**. Приложение само находит
артистов, обложки и текст песен через открытые каталоги, без ключей и без регистрации.

## Что внутри

### 1. Каталоги: iTunes → Deezer → MusicBrainz / Cover Art Archive
- Три провайдера, спрашиваются по очереди, побеждает ответ с наибольшим доверием.
- Все три — без API-ключей. MusicBrainz идёт с обязательным User-Agent и жёстким лимитом 1 req/s
  (иначе бан по IP), для остальных — свои интервалы.
- Никогда не перезаписываем теги в самих файлах. Всё фетченное живёт в отдельной таблице
  `track_meta` в Room и накладывается поверх локальных тегов при чтении. Выключил тумблер —
  библиотека мгновенно вернулась к тому, что написано в файлах.

### 2. Матчинг, который умеет отказываться
- Имя файла чистится перед запросом: `03_Artist - Title (Official Video) [slowed].mp3` → артист и
  название отдельно.
- Оценка 0..1000, порог принятия 640. **Длительность — главный судья**: названия врут постоянно,
  длина — нет. Slowed-эдит на 20–40 % длиннее оригинала, то есть это ровно тот случай, когда
  название совпадает идеально, а обложка была бы чужой. Большой разрыв по длине ветирует
  идеальное совпадение имени.
- Отказ записывается в БД (`state`, `attempts`), поэтому один и тот же безнадёжный файл не
  дёргает сеть каждую загрузку приложения.

### 3. Дедупликация по альбому (новое в этой сборке)
Двенадцать файлов одного релиза раньше означали двенадцать запросов и двенадцать скачиваний одной
и той же картинки. Теперь: очередь сортируется по альбому, первый файл релиза платит за весь
релиз, остальные получают ответ **без единого запроса** (`adopt`), обложка копируется на диске
(`ArtworkCache.cloneCover`).
- Группировка **только по локальным тегам** album+artist, нормализованным. Это и есть аргумент
  безопасности: два файла с одинаковым тегом альбома — это два файла, которые сам таггер уже
  объявил одним релизом. Группировка по *фетченному* альбому позволила бы одной уверенной ошибке
  расползтись на десяток треков.
- Артист входит в ключ, потому что «Greatest Hits» и «Сборник» — названия, которые делят тысячи
  никак не связанных файлов.
- Название трека **никогда** не наследуется: общий альбом означает общую обложку и общего артиста,
  но не то, что два файла — одна запись.
- Унаследованный ответ пишется на один балл ниже ответа-лидера: он получен по наследству, а не
  проверен, и ручное «Уточнить» должно уметь их различать.

### 4. Ручной поиск в каталоге (новое)
`⋮ → Искать в каталоге вручную`. Автоматика намеренно осторожна и на библиотеке из эдитов и рипов
несколько сотен треков не опознает никогда. Для фоновой задачи отказ — правильное поведение, для
человека, который точно знает, что это за трек, — бесполезное. Поэтому здесь:
- показываются **все** ответы всех трёх каталогов, включая слабые, отсортированные «сначала с
  обложкой, потом по уверенности», с названием провайдера, альбомом и длиной на каждой строке
  (длина — то, чем отличают эдит от оригинала);
- поле поиска предзаполнено чистым «Артист — Название», а не сырым именем файла;
- поиск запускается кнопкой/Enter, а не по каждой букве: иначе это пятнадцать запросов на каждую
  нажатую букву к трём публичным API, один из которых банит по IP ровно за это;
- превью грузятся уменьшенными — размер зашит в сам URL у всех трёх провайдеров, так что
  миниатюра стоит правки строки, а не ещё одного API (`RemoteMeta.thumbUrl`). Полный размер
  качается только после выбора;
- миниатюры **не** попадают в дисковый кэш обложек: ничего ещё не выбрано, и запись пятнадцати
  отклонённых картинок в кэш, из которого рисуется библиотека, — это чужая обложка на экране;
- выбранное вручную пишется со score 1000, автоматика его больше не перебьёт, а кэш текста для
  этого трека сбрасывается (он был скачан для старого артиста).

### 5. Текст песни
- lrclib.net, без ключа. Синхронный LRC с подсветкой строки и автопрокруткой, обычный текст как
  запасной вариант.
- **Кнопка «Текст» в плеере** (новое): текст скачивался и экран существовал, но единственная дверь
  к нему была в меню «⋮» — не там, где человек ищет слова играющей сейчас песни. Нижняя панель
  плеера теперь `Очередь · Текст · Папки`, 13.5 sp вместо 15 (три подписи на 360 dp).
- Точка на кнопке — обещание: она горит только когда текст для **этого** трека уже в кэше, то есть
  нажатие, которое сразу что-то покажет, визуально отличается от нажатия, которое пойдёт спрашивать.

### 6. Уведомление и экран блокировки больше не врут (новое)
Экран читал артиста из оверлея и обновлялся сразу, а уведомление — из `MediaMetadata`, собранного
при создании очереди, то есть за минуты до первого ответа каталога. Получалось «Аня Покров» в
приложении и «Неизвестный артист» на локскрине для одного трека — раскол, который читается как
сломанное приложение, а не как два пути данных. Теперь исправленные данные доезжают в живую
очередь (`PlayerController.refreshMetadata`): трогаются только элементы, чей текст реально
изменился, дебаунс 1.2 с (за время прохода — одна прогулка по таймлайну вместо трёхсот),
`replaceMediaItem` с тем же URI — это обновление метаданных, а не пере-подготовка, так что
воспроизведение не прерывается.

### 7. Плашка «Дополняем библиотеку» (новое)
Обложки и артисты, появляющиеся по одному через минуты после запуска, без объяснений на экране,
читаются как глюк. Теперь тонкая плашка сверху: `Дополняем библиотеку · 34 / 287`, тёмная, а не
акцентная (не должна конкурировать со списком), с фейдом (плашка, выскакивающая во время скролла,
крадёт взгляд), и задерживается на «Готово · дополнено N» — индикатор, исчезающий в момент
завершения, никто никогда не читает.

### 8. Сеть под контролем пользователя
Тумблер в настройках, по умолчанию **только Wi-Fi**, полное отключение одним переключателем,
сброс кэша фетченных данных. Проход отступает, когда палец скроллит список (тот же контракт, что
у префетчера обложек).

## Чего в этой сборке НЕТ (честно)

1. **AcoustID / фингерпринт звука** — не сделан и в этой архитектуре сделан не будет. Для него
   нужен `fpcalc` (нативный chromaprint) в APK: это NDK-зависимость, +2–4 МБ и своя сборочная
   цепочка. Обещать его в Kotlin-патче было бы врать. Файлы вида `AUD-20240312.mp3` остаются на
   ручном поиске (пункт 4) — именно поэтому он и появился.
2. **Не проверено компилятором.** В песочнице нет Android SDK и закрыт egress, зависимости не
   тянутся. Проверено структурно: 26 файлов, 9273 строки, баланс скобок чистый, все новые символы
   имеют и объявление, и использование, сигнатуры сверены с BOM 2024.12.01 / Media3 1.5.1.
   Последнее слово — за твоим CI.
3. **API вживую не дёрнуты.** Из песочницы egress закрыт, allowlist пустой. Клиенты, разбор
   ответов, кэш и UI написаны по документации форматов. Первый реальный прогон — у тебя на
   телефоне. Если провайдер ответит не тем, что я жду, — пришли JSON, подгоню парсер под факт.
4. **Процент попаданий не измерен** и обещан не будет. Ожидание: мейнстрим — высокий, СНГ-рэп и
   TikTok-эдиты — заметно ниже, на них и рассчитан ручной поиск.
5. `replaceMediaItem` на играющем элементе — по документации Media3 1.5 бесшовно для
   прогрессивного источника с тем же URI. Если услышишь щелчок при обновлении метаданных — скажи,
   уберу обновление текущего элемента и оставлю только соседей.
