# v6.24.0 — загрузка стала файлом, меню перестало падать

`versionCode 43`, `versionName 6.24.0`. Базис — **6.23.0** (ЗИП из репы, `versionCode 42`).

Версия закрывает долги 6.23.0: меню трека получило пункты («Скачать», «Играть следующим»,
«Добавить в очередь») раньше, чем под ними появилась работающая механика. Это ремонт, а не
новые функции.

---

## 1. «Играть следующим» больше не роняет приложение

**Причина.** `MediaController.addMediaItem` не кладёт элемент в плеер напрямую: запрос уходит в
`MediaSession`, и сессия обязана спросить у своего колбэка, что именно добавить. Дефолтная
реализация `MediaSession.Callback.onAddMediaItems` в Media3 возвращает провалившийся future с
`UnsupportedOperationException` — библиотека прямым текстом требует переопределить метод, если
элементы приходят со стороны контроллера. В `PlaybackService` его не было вообще: до 6.23.0
очередь собиралась только через `setMediaItems`, и дыры не было видно.

Вторая половина той же поломки: `MediaItem`, прошедший через сессию, теряет `localConfiguration`,
то есть URI. Даже без падения в очередь лёг бы элемент, который нечем играть.

**Ремонт.** `PlaybackService`: `onAddMediaItems` и `onSetMediaItems` переопределены (второй — тоже,
потому что дефолтный реализован ЧЕРЕЗ первый и унаследовал бы то же поведение). Адрес переезжает в
`MediaItem.requestMetadata.mediaUri` — единственная часть элемента, которая гарантированно
переживает границу сессии, — и восстанавливается на стороне сервиса.

Файлы: `playback/PlaybackService.kt`, `playback/PlayerController.kt`.

## 2. Шторка закрывается одним жестом

**Было.** Меню трека открывалось с `partial = true`, то есть с двумя якорями. Системный жест
«назад» из раскрытого состояния сжимал лист до половины, и только второй жест его закрывал. Две
логики закрытия у одного окна.

**Стало.** Половинный якорь убран вместе с параметром `partial` у `ZiziSheetScaffold`: у листа одно
состояние, любое раскрытие уезжает вниз с первого жеста, анимацией Material, а не исчезновением.

Файл: `ui/screens/Sheets.kt`.

## 3. Скачивание: теперь это настоящий файл в «Музыка/Zizi»

**Было.** «Скачать» писало байты в `SimpleCache` внутри `filesDir` — набор фрагментов `*.exo` с
бинарным индексом. Формально трек играл офлайн. Фактически файла не существовало: не видно в
файловом менеджере, нет в медиатеке телефона, нечего отправить, всё пропадает при переустановке.
Это был кэш под именем «загрузка».

**Стало** (`playback/OfflineStore.kt`, новый):

| | |
|---|---|
| Куда | публичная папка **`Музыка/Zizi`**, один файл на трек |
| Как (API 29+) | `MediaStore.Audio` + `RELATIVE_PATH`, запись под `IS_PENDING=1`, флаг снимается после последнего байта — недокачанный файл не виден НИКОМУ, поэтому обрыв не может оставить «битый трек» в медиатеке |
| Как (API 26-28) | обычный файл + `MediaScanner`; `WRITE_EXTERNAL_STORAGE` в манифесте ограничен `maxSdkVersion="28"` |
| Имя | `Исполнитель - Название.<ext>` |
| Расширение | по первым байтам потока (`AudioFormatSniffer`): m4a / mp3 / ogg / webm / flac / wav. Не по настройкам качества и не по заголовку ответа — и то и другое врёт, а файл будут открывать чужие приложения, которые верят расширению |
| Индекс | `filesDir/offline-index.json`, но истина на диске: запись без файла молча выпадает (человек вправе удалить файл проводником) |

Про формат честно: перекодировать в mp3 на телефоне без ffmpeg нельзя, поэтому файл сохраняется
как есть — обычно AAC в контейнере `.m4a`. Открывается везде, где открывается mp3.

Воспроизведение: слой кэша загрузок из цепочки источников убран, вместо него
`OfflineFirstDataSource` — одна проверка в момент открытия: есть файл — играем файл, нет — идём в
сеть. «Наполовину офлайн» как состояние больше не существует.

## 4. Загрузка выживает при сворачивании

`playback/DownloadService.kt` (новый) — foreground-сервис на время загрузок: уведомление с
процентом и кнопкой «Отменить», гаснет сам, когда активных загрузок нет. Раньше загрузка была
обычной корутиной в процессе приложения: система освободила память — и «скачал на дорогу»
обнаруживается уже в метро.

Плюс: одновременно качаются **два** трека, остальные показываются как «в очереди» (десять потоков
на LTE — это десять медленных загрузок вместо двух быстрых).

## 5. «Поделиться» отправляет файл

`MainActivity.shareTrack` — три ветки вместо двух:

1. **скачанный сетевой трек** → вложение: `EXTRA_STREAM` + `ClipData` + `FLAG_GRANT_READ_URI_PERMISSION`
   (без `ClipData` часть мессенджеров получает `SecurityException` у себя — снаружи это «пришло
   пустое вложение»), MIME из хранилища;
2. **сетевой не скачанный** → текст. В `uri` лежит внутренний `zizi://`, его не понимает ни одно
   приложение на телефоне;
3. **свой файл** → как было.

Подпись быстрой кнопки меняется на «Файлом», когда файл действительно есть. Обещать вложение там,
где его нет, хуже честной надписи.

## 6. Переходы у «Скачать» перестали дёргаться

**Было.** Пять разных `MenuItem` в `when`. Смена состояния меняла одновременно иконку, текст,
наличие второй строки и, из-за неё, высоту ряда — мгновенно. Список подпрыгивал. Проценты
публиковались `CacheWriter`'ом десятки раз в секунду.

**Стало** (`DownloadMenuItem`):

- ряд один, высота фиксированная (64.dp), вторая строка есть всегда — прыгать нечему;
- смена фазы (нет копии → в очереди → качается → скачано) — crossfade иконки и текста, 200-220 мс;
- прогресс — кольцо вокруг иконки через `animateFloatAsState` (420 мс, `FastOutSlowInEasing`):
  шаг процента виден как движение, а не как подмена цифры. Длина неизвестна — кольцо крутится;
- прогресс публикуется не чаще раза в 120 мс.

## 7. Заодно: тап по очереди играл не тот трек

Экран очереди показывает не таймлайн плеера, а результат сопоставления его id с библиотекой. Трек,
которого в библиотеке нет (найден поиском и добавлен в очередь), из списка выпадал, после чего
номера строк на экране и номера элементов в плеере расходились. `onPick` переведён с номера строки
на идентификатор (`PlayerController.seekToTrack`).

## 8. Отчёт о сбое

`CrashLog` (новый): стек последнего падения пишется в `filesDir/crash-last.txt`, в настройках
появляется строка «Отчёт о последнем сбое» — только если приложение действительно падало.
Ничего не отправляется само: ни сети, ни телеметрии, ни идентификаторов. Уходит текстом, когда
человек сам нажал.

Мотив прямой: три вылета подряд разбирались по описанию «нажал и вылетело», а угаданная причина
лечится заплаткой рядом с настоящей.

## Уборка при обновлении

`LegacyOfflineCache.purgeOnce` сносит старую папку `filesDir/zizi-offline` (у активного слушателя
это легко пара гигабайт, которые не видно ни в одном экране и не удалить ничем, кроме сброса
данных). `OfflineStore.cleanupPending` убирает `IS_PENDING`-строки, оставшиеся после убитого
процесса. Обе операции — один раз, на IO, не блокируют запуск.

**Плата:** треки, скачанные до 6.24.0, придётся скачать заново. Восстанавливать из фрагментов
`*.exo` нечего — они бесполезны без внутреннего индекса Media3. Зато теперь у загрузки есть файл,
который видно.

## Что проверить на устройстве

1. Меню трека → «Играть следующим» и «Добавить в очередь»: не падает, трек реально играет.
2. «Скачать» → появился файл в «Музыка/Zizi», виден в файловом менеджере и в чужом плеере.
3. Отключить сеть → скачанный трек играет мгновенно.
4. «Поделиться» у скачанного → уходит вложение, а не текст.
5. Жест «назад» из полностью раскрытого меню → закрывается сразу.
6. Свернуть приложение во время загрузки → уведомление с процентом, загрузка доходит до конца.
7. Остальные пункты меню (исполнитель, таймер, сведения, очередь, убрать из Zizi) — на вылет.
