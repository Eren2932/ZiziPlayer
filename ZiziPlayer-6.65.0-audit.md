## 1. Автоскип: подтверждённая причина в Android

`app/src/main/java/app/ziziplayer/playback/PlayerController.kt:300–338`, `handlePlayerError`:

После исчерпания восстановления перемотки любой PlaybackException увеличивает consecutiveErrors. Для remote item при наличии следующего элемента и допустимом счётчике вызываются `seekToNextMediaItem`, `prepare`, `play`. Причина ошибки НЕ проверяется. Поэтому исправление классификации одного только 403 не защищает очередь от DNS, timeout, 404, 5xx и других ошибок.

Граница исправления: переход к следующему треку не должен быть действием обработчика ошибки. Сохранить текущий mediaId, индекс и позицию; после ограниченных попыток восстановления остановить загрузку/показать причину и повтор. Естественное окончание трека и явная команда «Следующий» должны работать отдельно. Безопасная политика по умолчанию — ноль автопереходов по ошибке, включая неизвестные ошибки: сериализация Media3 между service/controller может не сохранить пользовательскую цепочку causes полностью.

Не заменять skip бесконечными retry. На 401/отозванный доступ нужен путь восстановления авторизации, на bot-check — пауза и серверная диагностика, на DNS/timeout — ограниченный retry с backoff. На 404 нет смысла бесконечно переспрашивать тот же cached videoId; возможен ограниченный поиск другой загрузки той же версии, но не переход в очереди.

`RemoteLoadErrorPolicy` в `ZiziDataSources.kt:133–187` не решает эту задачу: UNAVAILABLE прекращает повторы, а специальная HTTP-ветка работает с InvalidResponseCodeException. Ошибка JSON /resolve приходит через CatalogException и не обязана попасть в ту же ветку, что отказ самого /stream.

## 2. 403 не доказывает бан IP

`ZiziResolve.kt`, `resolve`: любой status 403 подписывается как «сервер получил бот-чек YouTube», а detail теряется. Но `server/zizi_resolver.py:890` возвращает 403 также для `device revoked`; произвольный 403 может быть ответом reverse proxy. Бот-чек — отдельная ветка `classify`, строки 430–451.

Потеря Authorization при обычной конфигурации этого backend скорее ведёт к 401 `bad token`/`device token required`, а не автоматически к 403. Nginx по умолчанию передаёт большинство входящих заголовков; отсутствие явного proxy_set_header Authorization само по себе не доказательство ошибки.

Нужны: content type и безопасная причина ответа /resolve, request ID, Nginx status/upstream_status, request_time/upstream_response_time, соответствующая строка backend журнала. Проверка через localhost и HTTPS должна использовать тот же id и ту же учётную запись устройства. Разовый 403 не доказывает постоянный IP-бан; возможны bot challenge, авторизация устройства, локальное правило Nginx/WAF и другие причины.

Предлагаемый контракт: отдельные поля stage, code, retryable, retry_after_seconds, request_id. HTTP 403 оставить транспортным статусом, а BOT_CHECK/DEVICE_REVOKED/ACCESS_DENIED различать машинными кодами. Не передавать пользователю необработанный stderr yt-dlp или signed URL: требуется редактирование чувствительных данных.

## 3. Серверный кэш отказов и ложные приговоры

`server/zizi_resolver.py:828–850`: soft определяется как code in (451,429), следовательно 403 bot-check по умолчанию кэшируется как hard на NEG_TTL=600 секунд. Offline-воспроизведение подтвердило `soft=false`, TTL около 600 секунд. Клиентский retry через 400 мс не исправляет такой cached отказ.

`_video_exists`, строки 467–490: oEmbed 400/401/403/404 возвращают False. В дальнейшей логике это считается подтверждением отсутствия видео. Offline-воспроизведение подтвердило, что 403 превращается в False. Отказ доступа не является доказательством удаления. Даже 404 следует трактовать осторожно: это максимум сигнал недоступности endpoint/resource, а не математическое доказательство постоянного удаления записи.

Исправление: неопределённый отказ проверки — UNKNOWN, не GONE. Не оставлять исходный ambiguous 404 окончательным при неизвестном результате арбитража. Для временных общесервисных отказов — короткий cooldown/ограничение повторов; не утверждать, что трек удалён. Точная длительность cooldown — настраиваемая политика, не гарантированное время восстановления источника.

## 4. Поиск одновременно слишком строгий и небезопасно мягкий

`server/zizi_catalog.py:534–599`: strict требует равенства version tags, всех значимых слов названия, последовательности слов артиста в title/uploader и длительности в окне:

$$|D_c-D_q| \leq \max(5,\min(12,0.04D_q))\text{ секунд}.$$

Для 180 секунд допустимо 7.2 секунды; для 240 — 9.6. Это не измерение акустического совпадения, а эвристика по метаданным.

Проверенная перезаливка с названием `Artist - Song (Ultra Slowed)` от `Random Channel` допускается строго: uploader не обязан быть официальным. Но если в названии только `Song (Ultra Slowed)`, а артиста нет ни там, ни в имени канала, оба режима отвергают результат. Разница длительности 240→280 также отбрасывается, даже при одинаковой метке Ultra Slowed.

Fallback по умолчанию включён в исходниках (ZIZI_STRICT_FALLBACK), но его наличие/значение на VPS не проверено. Он запрещает дополнительные теги кандидата, но допускает исчезновение запрошенных тегов. В fallback нет минимального score: `-1000` за несоответствие скорости не является окончательным запретом.

Результаты исполнения неизменённого production matcher с фикстурами:

| Запрос | Единственный кандидат | Результат |
|---|---|---|
| Song (Ultra Slowed), 240 s | Artist - Song (Ultra Slowed), другой канал, 240 s | strict success |
| Song (Ultra Slowed), 240 s | то же название без Artist, другой канал | 404 |
| Song (Ultra Slowed), 240 s | Artist - Song (Ultra Slowed), 280 s | 404 |
| Song (Ultra Slowed), 240 s | Artist - Song, 220 s | 404 |
| Long Song (Ultra Slowed), 240 s | Artist - Long Song, 220 s | fallback на оригинал, score=-1000 |
| Song (Slowed), 180 s | Artist - Song, 180 s | fallback на оригинал, score=-1000 |
| Song (Alice Remix), 180 s | Artist - Song (Bob Remix), 180 s | fallback на другой ремикс |

Различие Song/Long Song обусловлено условием «половина слов запроса найдена». Это объясняет нестабильное поведение названий, но не доказывает, что конкретные треки пользователя упираются именно сюда: нужны их metadata/IDs и фактическая выдача.

Android `DeezerCatalog.resolveStream:245–266` читает только vid и не использует fallback/confident/picked для объяснения подмены.

Предлагается: отдельно определять базовую композицию, артистов/ремиксера и версию. Издательские пометки и имя канала — не идентичность записи. Противоречащая версия/именованный ремиксер — запрет; отсутствие метки — неопределённость, не автоматическое доказательство совпадения. Нормализовать slow/slowed, разделители и согласованные синонимы; пороги длительности настраивать на реальных примерах, не просто расширить всё до 20%. Сначала найти ту же версию у другого uploader. Подмена оригиналом — только отдельная явно выбранная пользователем политика.

После изменения правил необходим новый MATCH_POLICY/cache namespace, чтобы старые miss/fallback записи не сохраняли прежнее поведение. Массовая очистка всех кэшей не нужна и создаст нагрузку.

## 5. Что действительно измеряют логи

`StartupTrace.java:28–44`: префикс `48218 ms | ...` — время с начала trace процесса, НЕ продолжительность запроса. Продолжительность записывается как `took=N ms`. Без полного лога нельзя утверждать, что упомянутые 48218/50771 ms — два запроса по 48–50 секунд.

`OfflineFirstDataSource.openNetwork` в `ZiziDataSources.kt:222–229` оборачивает network.open, а ниже располагаются CacheDataSource и ResolvingDataSource. Поэтому NETWORK_OPEN включает работу cache/match/resolve/open и не равен чистому TCP/TLS или времени только /stream. Складывать NETWORK_OPEN+MATCH+RESOLVE нельзя: spans вложенные.

`AUDIO_LOADING` ставится при BUFFERING, а также при IDLE+playWhenReady (`PlayerController.kt:375–379`). Сам по себе этот маркер не доказывает голодание буфера: он встречается и при запуске/ошибке. Для rebuffer нужны state, bufferedDuration, position, bytes/sec и причина перехода.

DNS took=25ms означает быстрое UnknownHostException на стороне HTTP клиента, не HTTP 403. Это может быть cached negative DNS/network transition и другие причины. Нельзя автоматически приписывать его МТС, серверу или бану источника.

Для аналитики нужны отдельные request/playback-attempt IDs и spans: DNS, connect, TLS, headers/TTFB, body read, server extractor queue/work, match, resolve, stream open. Не логировать токены/полные signed URL.

## 6. Буфер, бюджет времени и качество

Текущий loadControl: min 20s/max 90s, старт 1.5s, после rebuffer 3s. При 128 kbit/s полезный аудиопоток около 16 kB/s; 1.5s — около 24 kB аудио, 3s — около 48 kB, 90s — около 1.44 MB (без накладных расходов/изменения битрейта). Наличие maxBuffer=90s не означает, что он реально заполнен.

При средней скорости доставки V ниже скорости расходования R запас B исчерпывается примерно за B/(R−V), если обе скорости и начальный запас фиксированы и выражены в согласованных единицах. Больший стартовый буфер откладывает остановку, но не исправляет V<R. Нужны измерения на холодном/тёплом серверном кэше, отдельно от локального кэша телефона.

Клиентские resolver metadata calls не имеют общего callTimeout в resolverClient; match имеет отдельный slowClient. Серверный RESOLVE_BUDGET=18s — мягкий бюджет до начала следующей попытки, не hard deadline текущего yt-dlp thread; это прямо подтверждается кодом и тестом. Простое сокращение readTimeout не прекращает гарантированно серверную работу и может только умножить запросы.

RESOLVE не передаёт quality на сервер: quality.targetKbps используется как запасное значение метаданных bitrate, не как доказательство изменения реального кодирования. Не обещать адаптацию качества одной настройкой буфера.

## 7. Проверки и пределы выводов

Выполнены четыре исходных набора: 30 strict + 11 metadata + 17 fallback + 8 resolver = 66 успешных тестов. Это unit/fixture tests production-функций с SQLite и HTTP/yt-dlp заглушками. Они НЕ проверяют реальную выдачу YouTube, Nginx, Android/Media3 или МТС. Некоторые тесты прямо закрепляют нынешнюю нежелательную подмену Slowed оригиналом: зелёные тесты не равны подходящей продуктовой политике.

Дополнительно выполнен `reproduce_6650.py`: 7 сценариев matching, 7 контролируемых oEmbed статусов и проверка TTL bot-check. Полные наблюдения — observations.json. Этот скрипт записывает фактическое поведение исходной версии, а не regression-тесты будущего исправления.

Исходники не изменены. APK не собран; сервер не изменён; полный пользовательский лог и действующий конфиг Nginx не получены. На IP-бан, состояние VPS и устранение сетевых задержек выводов о подтверждении нет.

## Следующий этап

Первый patch: исключить переход очереди из обработчика ошибок, сохранить естественный конец/ручной next, сделать ограниченные повторы на том же элементе и понятное состояние остановки. Далее — типизированные причины отказов, безопасная диагностика и коррекция серверного negative cache/oEmbed. Изменение поиска согласовать отдельно: сохранить выбранную версию или разрешать замену с подтверждением.

Для серверной диагностики потребуется один полный свежий trace, безопасные строки access/backend log одного сбоя, фактический server/catalog version и обезличенный server/location block Nginx. Для matching — 3–5 проблемных треков с точным названием, артистом, длительностью/ID и примером ожидаемой загрузки. Authorization, cookies, приватные ключи и signed media URL присылать не нужно.
