## Что действительно расширено

Android использует LRCLIB и lyrics.ovh, а при настроенном `LYRICS_SERVER_URL` — также отдельный ZiziLyrics. На сервере общий дополнительный поиск выполняет NetEase. Официальные YouTube-описания подключены только через реестр предварительно проверенных привязок: сейчас одна запись, Senemene. Это **три общих внешних каталога плюс один узкий путь**, а не четыре универсальных поисковика.

NetEase сначала ищет название вместе с исполнителем, затем при отсутствии подходящих кандидатов — только название. До 20 записей на страницу, до двух поисковых и двух lyric-запросов в общем deadline источника 4.5 с. Дубликаты ID исключаются; кандидаты выбираются по близости длительности. Ошибка одного lyric-кандидата не уничтожает обычный текст от предыдущего (429 остаётся отдельным сигналом остановки и backoff). Не снимаются remix/slowed/live ради ложного совпадения.

Обычный текст можно показать сразу и продолжить поиск LRC. Сервер → LRCLIB → OVH; бюджеты 6 + 20 + 8 секунд, общий UI-предел 45 секунд включает ожидание приоритета аудио. Пригодный синхронный результат завершает поиск. Проверенный plain кэшируется 5 минут, а не месяц. Пустые ответы, ошибки, rate limit и подтверждённое отсутствие текста различаются.

Credits-only и известные заглушки не считаются словами. Неоднозначные или неподдерживаемые таймкоды, неизвестная длительность, несовместимая длительность и нарушенная последовательность не дают включить синхронный режим. Offset/enhanced/multiple-tag LRC сервер пока консервативно понижает до plain — это ограничение, не полноценная поддержка всех форматов. Android-импорт LRC сохранён.

## Исправление, критичное для сборки

Копия `.github/workflows/build.yml` в `repo-update` ранее отставала: в ней отсутствовала передача `LYRICS_SERVER_URL` и запуск серверных тестов. Копии синхронизированы, равенство проверяется тестом. ## Как включить новый серверный путь

1. Развернуть **отдельный** каталог `src/lyrics_server` по `lyrics_server/README.md`: Python 3.11+, отдельный systemd-сервис и HTTPS vhost. Проверить право использования источников. Не заменять аудиорезолвер или accounts_server.
2. В GitHub Settings → Secrets and variables → Actions → Variables задать `LYRICS_SERVER_URL=https://YOUR-LYRICS-HOST/`. Это публичный базовый URL, без `/v1/lyrics`, query, credentials и fragment.
3. Из `src/repo-update/.github/workflows/build.yml` обновить **корневой** `.github/workflows/build.yml` репозитория. Workflow внутри ZIP GitHub сам не запускает.
4. Положить итоговый `ZiziPlayer-v6.63.0-lyrics-lab.zip` в корень репозитория и запустить Actions. **Не загружать вместе с ним recovery-checkpoint ZIP с тем же versionCode**: селектор намеренно запрещает два максимальных кандидата.
5. Дождаться Android unit tests, компиляции instrumentation tests, assembleRelease и проверки подписи. Только после этого проверять APK на телефоне.

При локальной сборке используется установленный Gradle 8.11.1 и Android SDK:

````bash
gradle :app:testDebugUnitTest :app:compileDebugAndroidTestKotlin
gradle :app:assembleRelease -PlyricsServerUrl=https://YOUR-LYRICS-HOST/
````

Сборка без URL сохраняет два старых источника и **не даёт новый серверный NetEase/описания**. Серверный URL и выпуск APK в этом диалоге не настроены. VPS и GitHub не менялись.

## Как проверять не одну песню

Добавлен `lyrics_server/benchmark.py`, который принимает пользовательский CSV `title,artist,durationMs` и измеряет ответы развёрнутого сервера. По умолчанию требуется минимум 20 уникальных записей; для осмысленной проверки рекомендуются 100–300 разных треков из реальной медиатеки. Это не статистическая гарантия для мирового каталога.

Отчёт отдельно считает plain, `sync_returned_unverified`, miss, error и задержки; слова не сохраняются. Проценты относятся только к переданному списку. Сам benchmark НЕ включает Android LRCLIB/OVH и НЕ проверяет соответствие вокалу — полный гибрид дополнительно проверяется на устройстве. Инструкции находятся в README сервера.

## Что пока не решено

Нет универсального автоматического поиска по YouTube-описаниям, подключённых лицензированных каталогов, ASR/forced alignment или массовой собственной базы проверенных LRC. У Senemene пока нет проверенных таймкодов. Не гарантируются тексты для всех треков и правильность синхронизации по одному совпадению длительности. Недоступный источник, неверные теги, другая аудиоверсия и отсутствие текста остаются реальными причинами пропусков.

Следующая граница приёмки: развёрнутый сервер + Android CI + контрольная медиатека + прослушивание синхронизации. Этот ZIP позволяет продолжить работу без потери исходников, но не подменяет этот этап обещанием «100% покрытие».
