# ZiziPlayer 6.15.0 (versionCode 30)

Обмен плейлистами. До этой версии `share/PlaylistShare.kt` был написан целиком и **не вызывался ни
из одного места** — формат существовал, обмена не существовало. Теперь плейлист можно отправить и
принять, без сервера и без домена.

## Отправка

Кнопка «Поделиться» в строке плейлиста (`Плейлисты` → строка → значок отправки). Лист показывает
числа **до** отправки: сколько треков, сколько уедет с паспортом `provider/remoteId`, сколько
поедет только названием и будет искаться у получателя, и сколько это примерно килобайт.

Два транспорта, потому что выбирает не разработчик, а мессенджер получателя:

* **Файлом** — `.zizi` пишется в кэш, отдаётся наружу через `FileProvider` (`${applicationId}.files`,
  ровно одна папка в `res/xml/file_paths.xml`) с разовым разрешением на чтение. Файлы старше суток
  подчищаются при следующей отправке.
* **Строкой** — `ZIZI1:<base64(gzip)>` в буфер обмена. Это не «на всякий случай»: часть мессенджеров
  переименовывает вложения и подменяет MIME, и файл на другом конце перестаёт быть плейлистом.

Едут названия и паспорта треков, а не музыка. Лимит формата — 300 треков / 256 КБ, при переполнении
лист честно предупреждает, что уедут первые 300.

## Приём

Четыре входа, из которых два работают всегда, а два — для удобства:

| Вход | Работает |
|---|---|
| `Плейлисты` → **Импорт плейлиста** → «Из файла .zizi» | всегда: системный выбор файла, никаких фильтров |
| `Плейлисты` → **Импорт плейлиста** → «Вставить строкой» | всегда: поле заполняется из буфера сразу |
| Открыть присланный `.zizi` из мессенджера или проводника | `intent-filter` по расширению |
| Ссылка `zizi://p/<blob>` | `intent-filter` по своей схеме |

Фильтр по файлу сделан узким, по расширению. Широкий (любой `application/octet-stream`) поставил бы
Zizi в список «чем открыть» для **каждого** непонятного файла в системе. Обратная сторона: провайдер,
который не отдаёт имя файла в пути, до фильтра не долетит — на этот случай и существует «Из файла»
внутри приложения, он не зависит ни от чьих MIME.

`ACTION_SEND` для `text/plain` в манифест **не** добавлен сознательно: он засунул бы Zizi в шторку
«поделиться» при отправке любого текста из любого приложения. Строка принимается через буфер обмена —
на один тап больше, зато система остаётся чистой.

`MainActivity` переведена на `launchMode="singleTop"`: открытый из мессенджера файл иначе создаёт
вторую копию экрана поверх живой, с двумя ViewModel и «назад», ведущим в предыдущую копию того же
экрана. Интент помечается как обработанный (`EXTRA_HANDLED`) — без метки поворот экрана заново
открывал бы предпросмотр того же плейлиста, и уйти от него было бы нельзя.

## Экран предпросмотра — главное в этой версии

Плейлист **не создаётся молча**. Сначала лист построчно показывает, что получится:

* «уже на устройстве» — тот же трек нашёлся локально по названию и длительности (допуск ±3 с). Играть
  будем свой файл: он работает офлайн и не зависит от того, жив ли каталог;
* «приехал с паспортом» — `provider/remoteId` пришли в плейлисте, искать нечего;
* «нашёлся в каталоге» — догнали поиском;
* «не найден» — и это видно **до** создания, а не по жалобе получателя.

Название плейлиста можно поменять сразу здесь. Кнопка «Создать плейлист» активна, пока есть хотя бы
один трек, и не ждёт конца поиска: догонять каталогом двадцать чужих локальных треков может быть
долго, а плейлист из уже найденного человеку нужен сейчас.

Поиск по каталогу идёт **последовательно, с паузой 120 мс и потолком 60 запросов** на импорт. Пачка
параллельных запросов по плейлисту на 300 треков — это ровно тот трафик, за который провайдер
отвечает рейт-лимитом, и тогда не найдётся вообще ничего. Результат, пришедший после закрытия листа,
выбрасывается: состояние сверяется по идентичности.

Импортированные сетевые треки пишутся в `tracks` **без `savedAt`** — плейлист играет, но чужие треки
не подсыпаются в мои «Треки». Из подметания их спасает то, что они лежат в `playlist_tracks`, это
уже учтено в запросе `forgettableRemoteIds`. Room не менялся: схема та же, миграций нет.

## Заодно

`ZiziSheetScaffold`, `SheetTitle` и `MenuItem` в `Sheets.kt` стали `internal` вместо `private` —
новые листы обмена живут отдельным файлом `ui/screens/PlaylistShareSheets.kt` и переиспользуют те же
формы, а не рисуют четвёртую копию нижнего листа.

Строки предпросмотра выводятся `itemsIndexed`: один и тот же трек может лежать в плейлисте дважды, а
повторяющийся `key` в `LazyColumn` — это не косметика, это падение на месте.

## Что осталось за бортом

* **Сервер `ZiziResolve 1.4`**: `/playlist` с короткими кодами `ZIZI-7K4M`, рейт-лимит по IP на все
  ручки, ETag и `http-cache` для витрины. Файловый и строковый обмен работают полностью без него —
  короткие коды нужны только чтобы плейлист влезал в одно сообщение.
* Формат `PlaylistShare.kt` не менялся ни в одном байте: то, что уходит из 6.15.0, читается любой
  будущей версией с тем же `v: 1`.

## Проверено перед отправкой

Компилятора Android в песочнице нет. Поэтому: сверка всех проектных символов с импортами по пакетам
(с учётом `import пакет.*`) — ноль пропусков; проверка баланса скобок настоящим лексером, со
строками, символьными литералами и комментариями — ноль перекосов во всех файлах проекта; сверка
каждого использованного чужого API с его объявлением в коде (`withFallback`, `RemoteItem.Song`,
`playlistTracks`, `rememberRemote`, `MenuItem`, `SheetTitle`, `ZiziSheetScaffold`, палитра);
`material-icons-extended` в зависимостях есть — все использованные значки существуют. XML манифеста,
`strings.xml` и `file_paths.xml` разобраны парсером.
