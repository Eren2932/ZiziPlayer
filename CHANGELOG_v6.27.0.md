# 6.27.0 — «Поиск», пересобранный по замеру, и фирменный оранжевый

Три изменения, из которых одно — новая поверхность, одно — новая таблица, и одно — цвет,
который наконец перестал зависеть от обложки играющего трека.

---

## 1. Раздел «Поиск» переверстан по замеру референса

Не «в духе», а по пикселям. Все размеры сняты со скриншотов 1080 x 2400 при 2.628 px/dp:

| элемент | px | dp |
|---|---|---|
| поле поиска, высота | 136 | 51.8 |
| поля экрана | 43 | 16.4 |
| жанровая плитка | 477 x 287 | 181.5 x 109.2 |
| зазор колонок / рядов | 42 / 45 | 16 / 17 |
| радиус плитки | ~17 | 6.5 |
| карточка раздела (2x2) | 472 x 199 | 179.6 x 75.7 |
| портретная карточка | 364 x 538 | 138.5 x 205 |
| «Недавние»: обложка / шаг строки | 136 / 182 | 51.8 / 69.3 |
| центры «+» и «x» | 873 / 1012 | 332 / 385 |

**Ширина колонки считается, а не задаётся.** 181.5 dp на экране 411 dp — это
`(411 - 2*16.4 - 16) / 2`, то есть «две колонки в поле с зазором». Записать сюда константу
181.5 dp значило бы получить правильную сетку ровно на одном устройстве и кривую на всех
остальных. Пропорции при этом зафиксированы как отношения (1.663 у жанровой плитки, 2.372 у
карточки раздела), потому что пропорция — это и есть то, что скопировано с референса.

Структура хаба сверху вниз:

1. **Блок 2x2** — четыре входа. У референса здесь типы контента («Музыка», «Подкасты»,
   «Аудиокниги», «Мероприятия»), у нас тип контента ровно один, поэтому плитки отданы не
   типам, а входам: три готовых запроса и один личный — «Твоя волна», собранная из самого
   слушаемого артиста медиатеки. Подпись и запрос намеренно разные: «Новинки» находит мусор,
   `new music 2026` находит новинки.
2. **Полка «Открой новое для себя»** — портретные карточки 138.5 x 205, строятся из артистов
   собственной медиатеки, самых слушаемых первыми.
3. **Сетка из 24 жанровых плиток**, две колонки. Порядок неслучайный: первые шесть — то, что
   в этом приложении ищут чаще всего (фонк, русский рэп, замедленные, ускоренные, басс,
   бразильский фанк). Первый экран обязан закрывать большинство запросов без клавиатуры,
   иначе сетка — просто обои.
4. **Полки провайдера** — как были.

Обложка в углу плитки наклонена на 25 градусов и **уходит за правый край**. Это не украшение:
квадрат, целиком помещённый внутрь плитки, читается как иконка, и плитка превращается в
кнопку. Обрезка стоит на контейнере плитки, иначе тень поворота лезет в соседнюю колонку.

Картинки для плиток берутся из URL, которые провайдер уже прислал в подборки: реальные
обложки вместо заглушек и **ноль дополнительных сетевых запросов** — эти же байты рисуют полки
ниже и лежат в кэше.

### Поле поиска в двух состояниях

**Спокойное** (хаб): белая плашка 51.8 dp с тёмной подписью. Белая не по недосмотру: на тёмном
хабе поле обязано быть единственным светлым объектом — оно и есть вход в раздел, всё остальное
на экране материал.

**Сфокусированное** (недавние, подсказки): плашка гаснет до фона, слева появляется стрелка
назад. Клавиатура уже на экране, белый прямоугольник под ней не сообщает ничего, а стрелка
отвечает на единственный вопрос этого состояния — «как отсюда выйти».

### Что убрано

- **Лента чипов «Ты искал»** из хаба. См. пункт 2 — история переехала целиком.
- **MoodTile 64 dp.** Плитка без обложки неотличима от кнопки.
- **Блок «Из твоей медиатеки»** отдельной секцией: артисты не исчезли, они стали содержимым
  полки «Открой новое для себя».

## 2. «Недавние» — новая поверхность и новая таблица (миграция 7 -> 8)

До 6.27.0 память поиска состояла из строк: таблица `search_history`, двадцать запросов,
нарисованных горизонтальной лентой чипов. **Проблема ленты была не в том, что она
горизонтальная, а в том, что в ней лежало.** Человек ищет не «слова, которые я вводил», а «то,
что я вчера слушал», и между этими списками нет ничего общего: запрос `semp` не напоминает ни о
чём, строка `SEMPERO · Мини-альбом · QMIIR` с обложкой напоминает обо всём сразу.

Теперь есть стадия `SearchStage.RECENT`: тап по пустому полю открывает вертикальный список
того, что человек **открывал** — трек, альбом, плейлист, артист — с обложкой, типом и автором,
и запросы наравне с ними. Строка 69.3 dp, обложка 51.8 dp, справа «+» и «x».

«x» здесь появился ровно потому, что в строке 69 dp две цели по 44 dp расходятся на 53 dp по
центрам и промахнуться мимо «плюса» в «крестик» нельзя. В чипе высотой 38 dp это были бы две
команды ближе ширины пальца друг к другу — там забывание правильно жило на долгом нажатии.

### Таблица `recents`

Плоская, без внешнего ключа на `tracks`, и это сознательно — по той же причине, по которой во
всей базе нет каскадов (см. `MIGRATION_5_6`): `upsertTracks` работает через REPLACE, то есть
DELETE + INSERT, а `sweepRemote` регулярно подметает временные удалённые треки. Ссылка на
`tracks.id` умирала бы при каждом пересканировании и каждой чистке кэша, и «Недавние» пустели
бы сами по себе, без единого действия человека.

`key` — ключ идентичности, а не строка отображения: `t:r:<провайдер>:<id>` для трека,
`c:<провайдер>:<id>` для сборника, `q:<запрос>` для запроса. Один и тот же объект, открытый из
поиска, из полки и из альбома, обязан быть одной строкой, которая всплывает наверх, а не тремя
одинаковыми: REPLACE по этому ключу и делает всплытие.

Запоминание висит на **воспроизведении**, а не на «+». Это принципиально другое событие: «+»
кладёт трек в медиатеку и меняет `savedAt`, недавнее не кладёт никуда. Смешать их значило бы
либо засорять медиатеку прослушиванием (ровно то, чего проект избегает с 6.4), либо забывать
всё, что не сохранено, то есть почти всё.

### Три грабли миграции, на которые я не наступил

1. **Ни одного `DEFAULT`.** Значения по умолчанию у `RecentEntity` котлиновские, а Room кладёт
   DEFAULT в схему только для `@ColumnInfo(defaultValue = ...)`. Дописать `DEFAULT 0` значило бы
   разойтись с генерируемой схемой — и проверка идентичности отказалась бы открыть базу у всех,
   кто обновляется. Та же мина, о которую бились `MIGRATION_2_3`, `3_4` и `6_7`.
2. **Имя индекса строго по соглашению Room:** `index_recents_openedAt`.
3. **`key` в обратных кавычках** — Room генерирует именно экранированный вариант.

Индекс по `openedAt` стоит потому, что единственный запрос к таблице — «последние 30 по
убыванию времени», и без индекса это сортировка всей таблицы на каждом кадре подписки.

### Подсказки при наборе

Порядок жёсткий: сначала **свои** недавние, подходящие под набранное, затем догадки провайдера.
Своё всегда точнее чужого — человек уже был там, куда снова целится.

## 3. Фирменный оранжевый #F97316

`palette.accent` **не подошёл** и подойти не мог: он пересчитывается из обложки играющего трека
(`withAccent`), то есть «фирменный цвет» был бы цветом последней песни. Добавлены отдельные
`ZiziPalette.brand` и `onBrand`, которых не касаются ни `withAccent`, ни тонирование темы. Это
единственные константы палитры.

`onBrand` — почти чёрный `#1B0C00`, а не белый: контраст белого на #F97316 равен 4.0:1, ниже
порога AA для мелкого текста; у тёмного 8.9:1.

Где встал бренд: активный чип фильтра, галочка «сохранено», подсветка играющего трека, курсор в
поле, действия разделов, спиннеры, заполненные кнопки, иконка в шапке.

Поля добавлены со значениями по умолчанию — ни один существующий вызов конструктора палитры не
тронут.

## 4. Иконка приложения

Новый знак: чёрный «плей» из трёх скруглённых штрихов на брендовом оранжевом. Контуры обведены
с исходника 1254 x 1254 и упрощены до полилиний с допуском 1 px — при пересчёте в 108 единиц
это меньше десятой доли единицы, то есть меньше трети физического пикселя на 3x. Кривых Безье
нет намеренно: прямые сегменты с таким шагом дают тот же силуэт и не «плывут» при ручной правке.

Знак вписан в бокс 62 x 62 с центром (54,54) — та же геометрия, что была у «Z»: холст 108 x 108,
лаунчер вправе обрезать до 72 x 72, гарантированно переживают маску и параллакс центральные
66 x 66. Фон — плоский #F97316, тот же, что `ZiziBrand` в коде; второго источника правды у цвета
нет. Слой `monochrome` обновлён вместе с остальными, иначе на Android 13+ тематическая иконка
осталась бы старой буквой.

## Чего в этой версии нет

**Движка рекомендаций.** Полка «Открой новое для себя» пока построена на честной эвристике:
радио по самому слушаемому артисту медиатеки. Настоящий алгоритм — профиль вкуса по
`play_stats` и избранному с затуханием по времени, генерация кандидатов через `next`-эндпоинт
Innertube, скоринг, MMR-диверсификация, негативный сигнал по скипам — встанет ровно в это место
следующей версией и не потребует менять вёрстку.
