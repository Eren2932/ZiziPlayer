## Как устроен гибрид

DeezerCatalog принимает от каталога название, исполнителя, альбом, обложку, длительность и ISRC. Через `/match/deezer` сервер сопоставляет запись с YouTube videoId. Далее ZiziResolve получает аудиопоток, который воспроизводит Media3. Каталожные метаданные остаются идентичностью трека; длительность реального медиапотока уточняет длительность запроса текста в MainViewModel.

**LyricsRepository работает независимо: автоматические тексты берутся только из LRCLIB.** Приложение не получает тексты Deezer, не запрашивает вкладку текста YouTube Music, не читает субтитры ролика и не распознаёт вокал. Поэтому наличие песни в каталоге и работающий звук не гарантируют текст.

Порядок одного поиска: `/api/get` с точными метаданными и длительностью, затем `/api/search` по названию и артисту, затем по названию. Последний поиск всё равно проверяет исполнителя каждого кандидата. Не более трёх запросов на попытку; UI может повторить попытку, весь цикл ограничен 45 секундами. Каждый запрос ждёт готовности аудио, HTTP отменяется при смене трека. Синхронизация — по времени Media3; импортированный LRC — отдельная пользовательская ветка.

## Подтверждённые результаты двух треков

| Проверка | Raya (Ultra Slowed) — Zericxxn | Senemene — Dali Dade |
|---|---|---|
| Длительность на скриншоте | 130 секунд | Около 144 секунд (1:22 + 1:02) |
| LRCLIB точный запрос | Возвращает запись id 38647172 | HTTP 404 для 144 секунд |
| Поиск | По полному названию + артисту найдено; по Raya + артисту одна запись | Название+артист, название, артист и q=Senemene: четыре пустых массива |
| Данные текста | plainLyrics и syncedLyrics, instrumental=false | В проверенных ответах нет кандидатов |
| Правила исходной 6.61.0 | Для 130000 мс запись проходит | При пустой выдаче выбрать нечего |

Для Raya провайдер указал альбом `Raya (Versions)` и duration=130.0. Парсер исходного проекта принимает 32 отметки: первая 1740 мс, последняя 128530 мс. Есть построчные, но нет пословных временных отметок. Поэтому доступны существующие построчные переходы; настоящую пословную синхронизацию эти данные не дают. В момент 0:00 первая строка ещё не началась. Это не объясняет исчезновение всего блока, но важно для приёмки.

Числовые границы для Raya: синхронизированное отображение допускает абсолютную разность длительностей не более 2000 мс, то есть ожидаемую длительность от 128000 до 132000 мс включительно. При 132001 мс синхронизация уже выключается, но обычный текст ещё может пройти более широкую проверку. Для ожидаемых 130000 мс окно обычного текста составляет ±15000 мс. Название версии и артист проверяются независимо: запись Ultra Slowed нельзя автоматически выдавать за оригинальную Raya.

Проверка Java-политики и парсера выполнялась на настоящих временных отметках ответа с заменёнными на синтетические фразы текстами. Сами production-файлы LyricsMatchPolicy.java и LrcTimeline.java не изменены относительно 6.61.0. Полные тексты песен в новый ZIP не вложены. Совпадение с вокалом на слух и корректность пользовательской расшифровки LRCLIB не проверены.

Для Senemene дополнительно проверен точный публичный endpoint lyrics.ovh: HTTP 404. Он не подключён к приложению. Обычный поиск Deezer вернул нечёткую выдачу других песен; ни одна не использована как замена. **Из этих результатов нельзя заключить, что текста нигде в интернете нет.** Можно заключить, что существующий источник приложения не вернул его для проверенных метаданных.

## Что пока не установлено

Причина отсутствия Raya именно на телефоне **не воспроизведена**. Живой ответ сейчас существует, исходная Java-логика его принимает. Неизвестны установленная версия приложения, точные внутренние метаданные и длительность Media3, HTTP-ответы телефона, состояние автозагрузки и кэша во время скриншота. Ни VPN, ни буферизацию, ни серверный сбой нельзя объявить причиной без этих данных.

Возможные ветки видны в исходниках: автозагрузка отключена; ожидание запуска аудио; сетевая ошибка/429; истечение общего таймаута; иные метаданные/длительность; ранее сохранённый инструментальный ответ. Это гипотезы, не доказанный диагноз. Промахи хранятся в RAM 2 минуты, успешные внешние ответы на диске до 30 дней, импорт отдельно. Ручное «Обновить» обходит обычный кэш и кэш промаха, но не отменяет ограничение частоты провайдера.

## Что изменено

Добавлен ограниченный журнал одного поиска LyricsLookupTrace: метаданные текущего запроса, длительность, этап ожидания аудио, успешный HTTP или код ошибки, число результатов, причины отклонения кандидатов, выбранный id, признаки синхронизации и попадание в кэш. Он остаётся в памяти, автоматически никуда не отправляется. По окончании поиска его можно скопировать из настроек экрана текста. В буфер попадают также название/исполнитель/альбом — перед отправкой можно проверить содержимое. Тексты песен, полные URL запросов и заголовки авторизации намеренно не записываются.

Исправлена отдельная слабость резервного поиска: раньше временная I/O/5xx-ошибка `/api/get` завершала попытку до `/api/search`. Теперь поиск может продолжиться в пределах прежнего лимита запросов и общего таймаута. Если точный запрос упал, а резервные ответы пусты, сохраняется ошибка, а не ложный отрицательный результат. HTTP 429, прочие 4xx кроме 404, отмена и ожидание аудио не обходятся. Это улучшение устойчивости, **не доказательство, что именно этот дефект вызвал скриншот Raya**.

Сообщение при отсутствии кандидатов уточняет: подходящего текста не нашлось в LRCLIB, а не «текста не существует». Версия — 6.61.1-lyrics-exp / 116. Добавлены fixtures и тесты, обновлены активные version assertions; проверка формата версии теперь разрешает ровно этот экспериментальный суффикс. Аудиотракт, серверы, Room, DSP, правила совпадения и анимации не изменены. Новых сетевых провайдеров и зависимостей нет.

## Проверки и ограничения

Успешно выполнен tools/check_selftest.py вместе с подключёнными проверками проекта, включая новый test_lyrics_6611.py. Новая группа: четыре Python unittest, внутри — 22 исполняемые проверки production Java для Raya, границ синхронизации и ограничений журнала. Проверки Kotlin сетевого fallback в этой группе — проверки текста исходников, НЕ исполнение корутин/OkHttp.

Четыре существующие эвристические проверки Kotlin-синтаксиса, импортов, статических ссылок и аргументов прошли без замечаний. Дополнительно выполнены серверные проверки, перечисленные в verification/v6.61.1-lyrics-exp/additional-checks.json. Логи текущей проверки находятся в verification/v6.61.1-lyrics-exp. Старые verification-папки относятся к исходному архиву, а не к новой версии.

**Gradle, Kotlin/Compose компиляция, APK, эмулятор и реальный телефон здесь не проверены.** Доступен Java, но нет подготовленного Android toolchain. Успех source guards не заменяет сборку. Живые API проверены через загрузчик публичных URL, не из сети телефона. Реальное совпадение выбранного YouTube-аудио с текстом не проверено.

## Сборка и приёмка

Загрузить ZiziPlayer-v6.61.1-lyrics-exp.zip в корень своего репозитория. Существующий корневой workflow выбирает мобильный архив с максимальным versionCode; новый 116 больше исходного 115. Не должно быть второго архива с тем же максимальным кодом. Корневой workflow менять не требуется; current.json Desktop не трогать. Сам репозиторий и VPS из этого диалога не изменялись.

После успешной GitHub Actions-сборки установить APK с прежней подписью поверх приложения, без удаления данных. При несовпадении подписи не удалять старую установку ради проверки — исправить подпись сборки.

Включить автозагрузку текста. Открыть именно Raya (Ultra Slowed) — Zericxxn, дать аудио запуститься. Через меню плеера открыть текст, затем настройку текста, нажать «Обновить». Дождаться окончания поиска (до 45 секунд); нажать «Копировать диагностику». Повторить для Senemene. Передать оба журнала и номер установленной версии. Они позволят отличить сетевую ошибку, несовпадение метаданных/длительности, кэш и отсутствие записи.

Отдельно проверить переход первой строки Raya около 1,74 с, повторяющиеся строки, перемотку, быстрые переключения треков, паузу, отключение сети и отсутствие изменений в старых рабочих текстах. Если реальное аудио отличается вступлением/монтажом, одной близости длительностей недостаточно: такую синхронизацию нужно проверять отдельно, а не растягивать LRC вслепую.

Для появления Senemene нужен подтверждённый источник текста/LRC либо отдельная работа по расшифровке и разметке аудио. Подключение дополнительного поставщика имеет смысл после проверки покрытия, условий использования и наличия таймингов. Этот эксперимент не заявляет, что оба трека уже исправлены.
