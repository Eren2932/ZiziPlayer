# ZiziPlayer 6.44.0 — исправление компиляции Java-тестов

## Основа и диагноз

Основа: `ZiziPlayer-v6.44.0.zip` из коммита `cf33a66533fa6b4f8e82e59b2af7a554a785adca` публичного репозитория Eren2932/ZiziPlayer. Версия **6.44.0**, **versionCode 92** сохранена.

Источник диагностики: `unit-tests.log` из присланного владельцем `jvm-test-reports.zip`, запуск Actions 34765078141, job 103744492826.

В этом запуске успешно завершились `compileDebugKotlin`, `compileDebugJavaWithJavac` и `compileDebugUnitTestKotlin`. Падение произошло в `compileDebugUnitTestJavaWithJavac`:

````text
LrcTimelineChecks.java:65: error: cannot find symbol
    var lines = LrcTimeline.parse(Files.readString(Path.of(args[0])));
                                      ^
symbol: method readString(Path)
location: class Files
````

`Files.readString` доступен в настольном JDK, но отсутствует в API, с которым этот запуск компилировал Android-тесты. `sourceCompatibility = 17` и `jvmTarget = 17` не делают библиотеки Android тождественными настольному JDK. Предыдущая standalone-проверка компилировала Java с библиотеками JDK и не могла выявить это различие. Сам файл с ошибкой — тестовый; его необязательная CLI-ветка компилируется Gradle независимо от того, вызывается ли `main` при JUnit-прогоне.

## Изменения

В `LrcTimelineChecks.java` чтение заменено на:

````java
new String(Files.readAllBytes(Paths.get(args[0])), StandardCharsets.UTF_8)
````

Это сохраняет явный UTF-8 и использует более ранние API. Подпись диагностического вывода теперь говорит о LRC-файле, а не о live-provider: локальная фикстура не является проверкой провайдера.

В `tools/test_lyrics_6440.py` добавлен запуск необязательной файловой ветки на локальном LRC. Новый `tools/test_lyrics_file_api.py` подключён через уже вызываемый корневым workflow `tools/check_selftest.py`. Он проверяет отсутствие конкретного несовместимого API и компилирует/исполняет фактическое выражение чтения, извлечённое из исходного теста. При изменении структуры этой ветки проверку необходимо явно адаптировать.

Без аргументов новый тест выполняет проверку исходника и host-JDK-пробу, честно сообщает, что Android API не проверялся. Опция `--android-jar` включает компиляцию против настоящего Android bootclasspath: старый вызов должен не скомпилироваться, новый — скомпилироваться. Автоматических загрузок и новых зависимостей приложения нет.

**Ни один файл `app/src/main/`, ни `app/build.gradle.kts`, ни серверный исходник, ни workflow не изменён.** Алгоритм синхронизации, интерфейс, зависимости, ключи подписи и desktop-версия не затронуты. Это адресное исправление сборки, не новый функциональный релиз и не полный аудит проекта.

## Установка в существующий репозиторий

Загрузить полученный **`ZiziPlayer-v6.44.0.zip` целиком в корень репозитория с заменой файла с тем же именем**. Не распаковывать поверх корня и не оставлять второй исходный ZIP с versionCode 92: текущий workflow справедливо отклоняет два архива с одинаковым максимальным кодом. При замене содержимого ZIP push должен запустить Android workflow.

Desktop `current.json`, корневой workflow и секреты менять не требуется. Файл `jvm-test-reports.zip` не содержит Gradle-проекта и селектор его пропускает.

Дождаться нового запуска для нового коммита. Повторный Run старого запуска #418 использует старые исходники и исправление не проверит. Контрольные точки: `compileDebugUnitTestJavaWithJavac`, затем `testDebugUnitTest`, затем `Assemble release`. Если следующая стадия упадёт — нужен новый `jvm-test-reports.zip` / лог соответствующей стадии. Нельзя отключать тесты или скрывать их ошибки ради зелёной сборки.
