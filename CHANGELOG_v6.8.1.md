# ZiziPlayer 6.8.1 (versionCode 17)

Диагностический релиз. Ставит одну задачу: превратить «не работает» в строку, которую можно
прочитать целиком и скопировать. Плюс два фикса, которые не зависят от YouTube вообще, и одна
бесплатная попытка вылечить воспроизведение.

## 1. Полная диагностика потока (главное)

**Настройки → Сетевой каталог → «Полная диагностика потока»** (появляется после «Проверить
подключение»).

Было: вердикт печатался в подзаголовок строки настроек. Подзаголовок — две строки, поэтому
`LOGIN_REQUIRED «Войдите, чтобы подтвердить, что вы не робот»` доехало до пользователя как
`ANDROID_VR: Войдите в`, а вердикты остальных четырёх клиентов не показывались вообще. Диагностика,
которую нельзя прочитать, диагностикой не является — и это стоило целого релиза.

Стало: `RemoteCatalog.streamReport()` опрашивает **каждого** клиента, игнорируя доверие и отдых, и
докладывает по каждому:

```
ANDROID_VR @ youtubei.googleapis.com → LOGIN_REQUIRED «Sign in to confirm…» · форматов 0 (аудио 0, шифр 0) · ссылки нет
IOS @ youtubei.googleapis.com → OK · форматов 22 (аудио 4, шифр 0) · 129 кбит/с audio/mp4 · CDN HTTP 206 · audio/mp4 · bytes 0-1/3512044
```

Результат — в диалоге, монospace, со скроллом и кнопкой **«Скопировать»**.

Что означают исходы (разные болезни с одинаковым симптомом):

| Строка | Диагноз | Лечение |
|---|---|---|
| `LOGIN_REQUIRED` у всех | bot check | poToken через WebView |
| `OK · форматов 0` | SABR: форматов в ответе больше нет | смена архитектуры добычи |
| `OK · аудио N, шифр N` | ссылки за `signatureCipher` | нужен запуск JS-плеера |
| `OK … · CDN HTTP 403` | ссылка выдана, но не отдаётся | смена клиента/личности |
| `OK … · CDN HTTP 206` | тракт живой | искать ниже: декодер |

## 2. visitorData — недостающая половина каждого запроса

`visitorData` — это сессионная личность, которую Innertube выдаёт при первом контакте и ожидает
видеть во всех последующих запросах. **До 6.8.1 приложение её никогда не запрашивало и никогда не
отправляло**: каждый вызов — поиск, browse, player — приходил как новый анонимный клиент без
истории. Поиск это терпит. Endpoint `player` — ровно то место, где живёт bot check, и вызывающий без
сессии — его первый подозреваемый.

- `ensureVisitor()` — один запрос `visitor_id` на сессию (TTL 6 часов), best-effort: если не вышло,
  каталог работает как в 6.8.0;
- `harvestVisitor()` — личность подбирается бесплатно из ответов поиска и browse, так что в
  большинстве случаев отдельный запрос не нужен вовсе;
- уезжает и в `context.client.visitorData`, и в заголовке `X-Goog-Visitor-Id`.

Это **не** poToken и не выдаётся за него. Но это его обязательное условие: токен минтится под
конкретную `visitorData`. Если проверка ослабляется при наличии сессии — воспроизведение лечится
одним этим, бесплатно.

## 3. Клиенты: было 5, стало 8

Новые: **IOS** (основной, не музыкальный — другой путь аттестации, чаще всех отдаёт чистые ссылки),
**WEB_EMBEDDED_PLAYER** (embed — отдельное исключение из аттестации), **MWEB** (браузер телефона,
аттестовывать нечего).

Порядок: `ANDROID_VR → IOS → TVHTML5_SIMPLY_EMBEDDED_PLAYER → WEB_EMBEDDED_PLAYER → MWEB →
IOS_MUSIC → ANDROID_MUSIC → WEB_REMIX`.

Заодно:
- `X-Youtube-Client-Name` / `-Version` теперь отправляются для **всех** клиентов (в 6.8.0 — только
  для WEB_REMIX). Запрос, у которого заголовок и контекст расходятся в том, кто спрашивает, — плохой
  запрос;
- `Origin` / `Referer` для embed/MWEB/TV;
- `playbackContext.contentPlaybackContext` — только браузерным клиентам, потому что приложения его не
  посылают, а поле, которого настоящий клиент не отправил бы, — ещё одно отличие для bot check.

## 4. Обложек стало МЕНЬШЕ в 6.8.0 — вот почему

Не совпадение, а прямое следствие правки 6.8.0. Версионирование ключа `no_art` было верным решением
(старый набор был отравлен), но оно выбросило вердикты по всем 449 локальным файлам сразу. Фоновый
проход начал перепроверять каждый — а каждая проверка берёт разрешение у `diskGate`, которых **три**.
Сетевая плитка на экране просила разрешение у тех же трёх и вставала в очередь за сотнями локальных
перепроверок. Ничего не было сломано — сломан был светофор.

- сетевые строки читают диск через свои два разрешения (`remoteDiskGate`) — их больше нельзя
  заморить локальной индексацией;
- фоновый проход держит максимум **одно** разрешение `diskGate` (`prefetchGate`) — он больше не
  занимает весь дисковый этап;
- **ключ индекса намеренно НЕ поднят снова**: именно его подъём вызвал шторм.

Плюс: Innertube кладёт превью не на каждую строку (глубокие полки поиска, треклисты альбомов часто
приходят без него) — «обложки не везде» было настоящим, а не иллюзией кэша. Теперь адрес выводится:
`/vi/<id>/mqdefault.jpg`.

## 5. «ПАПКА НА УСТРОЙСТВЕ»

Захардкоженная строка над каждым треком, включая те, что текут с CDN. Для сетевого трека —
`ПОТОК ИЗ СЕТИ`. Подпись, которая врёт половине очереди, хуже отсутствия подписи: она отправляет
искать локальный файл, которого никогда не было.

## Порядок проверки

1. Собрать, поставить, убедиться: **Версия 6.8.1**.
2. «Проверить подключение» → должно быть `[yt] N шт. за 3 стр.`
3. **«Полная диагностика потока»** → дождаться, «Скопировать», прислать текст.

Этот текст назовёт слой без единого предположения — и решит, идём ли мы за poToken через WebView или
проблема уже ниже, в декодере.
