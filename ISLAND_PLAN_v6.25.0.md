# ZiziPlayer 6.25.0 — «Островок». План работ

**Базис:** `ZiziPlayer-v6.24.0-source.zip` (`versionCode 43`), Media3 1.5.1, compileSdk 35, Compose BOM 2024.12.01.
**Референс:** запись экрана HyperOS — «Умный островок» над Spotify: капсула в статус-баре с бегущей
строкой → раскрытие в плашку с таймером `00:20 / 07:04` и рядом транспорта (shuffle · prev ·
play/pause · next · «+») → схлопывание в пилюлю с живой волной.

**Решение по объёму:** делаем то, что не зависит от вендора — слой A (свой островок) + слой B
(правильное уведомление Android 16), с предварительным замером слоя C (HyperOS).
Слой C и слой D (оверлей) — отдельным релизом 6.26.0, только по результатам замера.

---

## Этап 0. Спайк-замер на устройстве (0.5–1 день)

Цель: получить ФАКТ вместо гипотезы. Ровно один вопрос: **отдаёт ли HyperOS островок нашей
медиа-сессии и/или нашему фокус-JSON без включения пакета в список Xiaomi.**

Собираем debug-сборку с экраном «Диагностика островка» (за DEV UNLOCK, как резолвер) и тремя
кнопками, каждая шлёт одно уведомление:

1. **Проба 1 — чистая медиа-сессия.** Уже есть в проекте. Запустить трек, свернуть приложение,
   зафиксировать: появилась ли капсула в статус-баре сама, без каких-либо MIUI-расширений.
2. **Проба 2 — `miui.focus.param`** (протокол HyperOS 1 / MIUI 13–14): обычный канал высокой
   важности, ongoing, JSON в `extras`, картинки отдельным `Bundle` `miui.focus.pics` как `Icon`.
3. **Проба 3 — `miui.focus.param.v2`** (протокол HyperOS 2: `basicInfo` / `timerInfo` /
   `actions` / `picInfo` / `aodPic`).

Что снимаем в отчёт (без этого замер не считается сделанным):

- точная версия HyperOS и Android на устройстве;
- скриншот/запись результата каждой пробы;
- `adb logcat` с фильтром по SystemUI: строки о разборе фокус-параметров и о причине отказа
  (whitelist / неверная схема / неподдерживаемый протокол);
- вывод в трёх словах: РАБОТАЕТ / ИГНОРИРУЕТСЯ / ПАДАЕТ.

**Развилка после замера:**
- проба 1 РАБОТАЕТ → островок для медиа даётся всем, слой C стоит ~1 день и делается в 6.25.0;
- проба 2 или 3 РАБОТАЕТ → слой C стоит 2 дня, идёт в 6.26.0;
- всё ИГНОРИРУЕТСЯ → слой C закрыт кодом, обсуждаем слой D (оверлей) отдельно.

Проба обязана быть безопасной: любой фокус-JSON строится в `runCatching`, отсутствие класса или
поля не должно валить сервис воспроизведения. Уведомление плеера важнее островка.

## Этап A. Свой островок внутри приложения (2–3 дня)

### Что есть сейчас

`ui/screens/LibraryScreen.kt:1124` — `MiniPlayer`: full-bleed полоса, высота `MINI_HEIGHT` (39 dp),
обложка 34 dp, две строки текста, две круглые кнопки, сверху `MiniProgressLine` (2 dp, прогресс
читается в фазе отрисовки через `drawBehind` — правильно, не трогать).
`MainActivity.kt:401` — вставлена в `Column` между контентом и `ZiziTabBar`, то есть физически
отбирает место у экрана и не может ни всплывать, ни морфиться.

### Что делаем

1. **Мини-плеер уезжает из `Column` в `Box`** поверх контента (как `ZiziSheetScaffold` уехал в
   `Popup` в 7.0). Место под него компенсируется `contentPadding` списка — механика уже есть,
   `hasMiniPlayer` в `LibraryScreen.kt:669`.
2. **Три состояния** в одном компоненте `ui/components/ZiziIsland.kt`:
   - `PILL` — узкая капсула: обложка + живая волна (эквалайзер из `Common.kt`, он уже без
     аллокаций в кадре);
   - `BAR` — текущий мини-плеер (название, исполнитель, play/pause, next);
   - `EXPANDED` — как на референсе: таймер `позиция / длительность`, бегущая строка, ряд
     транспорта shuffle · prev · play/pause · next · «+».
3. **Движение.** Морфинг ширины / высоты / радиуса — одной пружиной
   (`spring(dampingRatio = 0.85f, stiffness = 1600f)`, тот же профиль, что у листов в 7.0:
   ~180 мс без овершута). Сдвиг и масштаб — только через `graphicsLayer`, ни одного чтения
   анимируемого значения в композиции. Текст на переходе — crossfade 200 мс, как у
   `DownloadMenuItem` в 6.24, чтобы не мигал подменой.
4. **Жесты.** Тап по `PILL`/`BAR` → `EXPANDED`. Тап по `EXPANDED` в область текста → полный плеер.
   Свайп вверх → полный плеер (переиспользуем существующий `draggable` + `slide` из
   `MainActivity`). Свайп вниз из `EXPANDED` → `BAR`. Свайп в сторону → next/prev.
5. **Бегущая строка** — своя, на `graphicsLayer.translationX`, только когда текст реально не
   влезает, с паузой 1.2 с на концах. Готовой брать нельзя: `basicMarquee` даёт кадры без нашего
   контроля над паузами и на длинном названии выглядит дёргано.

### Обязательные правила (оплачены кровью в 7.1)

- **Закрытием/морфингом владеет состояние, а не корутина анимации.** `Animatable` отменяется любым
  вторым касанием; в 7.0.0 это дало невидимый `Popup`, съедавший все тапы в приложении. У островка
  касаний будет больше, чем у листа, — та же ошибка здесь стоит дороже.
- Любой эффект перехода — в `withTimeout(длительность + 120 мс)`.
- Пока идёт переход, обработчики жестов на источнике перехода отключены.
- Ни одного `pointerInput` на невидимом слое.
- Прогресс и позиция читаются только в фазе отрисовки — иначе островок будет рекомпоноваться
  дважды в секунду вечно.

### Приёмка этапа A

1. Морфинг `PILL ↔ BAR ↔ EXPANDED` без прыжков layout и без мигания текста.
2. Быстрые двойные жесты в момент перехода — приложение отвечает на тапы (регресс-тест из 7.1).
3. Скролл библиотеки на 3000+ треков с открытым островком — без просадки кадров.
4. Островок не перекрывает последний ряд списка и таб-бар.
5. Поворот экрана и возврат из фона сохраняют состояние островка.

## Этап B. Уведомление под Android 16 (1–1.5 дня)

### Что есть сейчас

`playback/PromotedNotificationProvider.kt`: `FLAG_PROMOTED_ONGOING` достаётся **рефлексией**,
потому что на compileSdk 35 константы нет. Флаг вешается только на playing-состояние — это уже
правильно (в прошлой версии уведомление было неснимаемым после паузы).

### Что не так

- promoted-статус в Android 16 присваивает система по своим правилам и по разрешению
  пользователя; нашим флагом его продавить нельзя — рефлексия здесь не механизм, а надежда;
- новых API (`Notification.ProgressStyle`, `setShortCriticalText`) в компиляции нет вообще;
- Live Updates у Google заявлены под прогресс-сценарии (доставка, навигация), медиа система ведёт
  своим медиа-чипом.

### Что делаем

1. `compileSdk` / `targetSdk` **35 → 36**, Media3 **1.5.1 → 1.8.x**, Compose BOM — свежий.
2. Рефлексию убрать, использовать нормальные API под `Build.VERSION.SDK_INT` гейтом.
3. Отдать системе полный набор данных для чипа: длительность, поддержка seek, обложка через
   `ZiziBitmapLoader`, короткий критический текст.
4. `FLAG_ONGOING` — по-прежнему только на playing. Не ломать.

### Риски бампа `targetSdk 36` (закладываем половину дня именно сюда)

- новые ограничения на foreground-сервисы — проверить `PlaybackService` (mediaPlayback) и
  `DownloadService` (dataSync) на живом устройстве, включая запуск загрузки из фона;
- обязательный edge-to-edge — проверить `statusBarsPadding` / `navigationBarsPadding` на всех
  экранах, включая свои `Popup`-листы;
- прогон всех пунктов приёмки 6.24.0 (меню трека, загрузка в «Музыка/Zizi», шаринг файлом).
