# ZiziPlayer 6.11.0 — «плеер, а не пульт управления сервером»

**versionCode:** 26 · **versionName:** 6.11.0 · **сервис:** ZiziResolve 1.3 (без изменений)

Функционально воспроизведение то же, что в 6.10.2. Меняется то, что видит человек,
который не участвовал в отладке гео-блока.

---

## 1. Резолвер вшивается в сборку

`app/build.gradle.kts` получил три поля `BuildConfig`:

| Поле | Откуда берётся | По умолчанию |
|---|---|---|
| `RESOLVER_URL` | `-PresolverUrl` / env `RESOLVER_URL` | `147.45.166.244:8080` |
| `RESOLVER_TOKEN` | `-PresolverToken` / env `RESOLVER_TOKEN` | пусто |
| `RESOLVER_PROXY` | `-PresolverProxy` / env `RESOLVER_PROXY` | `true` |

**Токена в репозитории нет и быть не может** — репозиторий публичный. CI передаёт его
секретом `RESOLVER_TOKEN`. Сборка без секрета остаётся рабочей: она просто оставляет поля
адреса и токена видимыми, как в 6.10.2.

Значение, введённое руками, по-прежнему главнее вшитого (`ifBlank`), так что старая
установка и человек со своим сервером не ломаются.

## 2. Настройки: 9 технических кнопок → 4 понятных

Группа «Сетевой каталог» разделена надвое.

Обычный пользователь видит группу **«Поток из сети»**: Качество потока, Только Wi-Fi,
Кэшировать потоки, Очистить кэш. Всё.

Скрыты: Свой резолвер, Токен резолвера, Гнать звук через сервер, Проверить сервер,
Источник, Полная диагностика, Отчёт о потоке, Активный поток.

Четыре пользовательские строки вынесены в общую функцию `StreamUserRows`, поэтому спрятать
техническую часть и случайно потерять их вместе с ней невозможно.

## 3. Режим отладки: семь тапов по версии

`Настройки → О приложении → 7 тапов по строке с версией` → возвращается вся техника.
С третьего тапа строка подсказывает, сколько осталось. Один тап в режиме отладки — выключить.
Флаг живёт в DataStore (`dev_mode`), переживает перезапуск.

Почему не удалить совсем: строка `/health` и «Полная диагностика» — единственный способ
отличить «сервер лежит» от «трек удалён» по скриншоту от пользователя, без кабеля и без
пересборки APK.

## 4. Подпись релиза доведена до рабочего состояния

Было: workflow брал `SIGNING_STORE_FILE` из секрета **как путь**. Путь к файлу, которого
на раннере не существует. То есть подпись фактически не работала ни разу, а `release`
собирался debug-ключом.

Стало:

- новый шаг `Decode keystore` — хранилище едет секретом в base64 и раскладывается в `$RUNNER_TEMP`;
- `signingConfigs` проверяет `isNullOrBlank()` и существование файла: GitHub отдаёт незаданный
  секрет **пустой строкой**, а `file("")` роняет Gradle с сообщением не по делу;
- новый шаг `Verify signature` — валит сборку, если в сертификате `CN=Android Debug`;
- тег `v*` публикует APK в Releases.

Инструкция целиком: `RELEASE.md` (создание ключа, 4 секрета + 1 переменная, выпуск тегом).

`.gitignore` пополнился `*.jks`, `*.keystore`, `keystore.properties`.
