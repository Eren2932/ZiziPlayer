# ZiziPlayer — статус тракта воспроизведения (STATUS.md)

**Дата:** 5 сентября 2026
**Версия приложения:** 6.37.3 (`versionCode 70`, `targetSdk 36`) — релиз **клиент + сервер**,
APK пересобирается. Вечный токен из APK больше не пропуск, а одноразовый ввод: клиент
завёл `installId` (`ZiziInstall.kt`) и меняет бутстрап-токен на короткоживущий ключ

**Токен в APK:** `ZIZI_TOKEN` по-прежнему лежит открытой строкой в каждом выпущенном APK
(в репозитории и git-истории его НЕТ — он приходит из секрета CI на сборке), но с 6.37.3 он
даёт ровно одно право: попросить себе ключ на `GET /auth/device`. Роут стоит в самом узком
классе квоты (`auth`, 5/12 и 3/6 с адреса), ключ живёт сутки, привязан к `installId` внутри
подписи и отзывается одной строкой в `zizi.env` без выпуска APK. Переключение режимов — по
цифрам из `/catalog/health`, не на глаз: `guard.anon_pct == 0` включает `ZIZI_TOKEN_MODE=require`,
`guard.device_pct == 100` включает `ZIZI_DEVICE_MODE=require`. После второго все 30+ выпущенных
релизов становятся безвредны сами, и менять `ZIZI_TOKEN` разом для всех уже не нужно.
По умолчанию оба режима — `warn`: старые сборки продолжают работать и считаются в долях.

### 2.6 Три «мёртвых» трека были живы. Классификатор врал

`oembed` (эндпоинт YouTube, который отвечает только за существование видео) сказал:

```
3ohcH7nUsoc  oembed 200  ← жив, yt-dlp врал «Video unavailable»
jwgZOOFljZc  oembed 200  ← жив
IM4v4sq8ypo  oembed 404  ← действительно удалён
xoKbls7K5og  oembed 200  ← жив, гео: список стран без RU + «use a VPN or a proxy server»
```

То есть `yt-dlp` под RU-паспортом выдаёт гео-блок текстом `Video unavailable` /
`This video is not available` — неотличимо от удаления. Наш `classify()` верил тексту буквально
и ставил `404` = «удалён», а `404` без ретрая на прокси означало смерть трека на 10 минут.

### 2.7 Google не верит `ipinfo`. Из 15 VLESS-узлов чистый один

Написан `server/tools/zizi-geoscan.py`: поднимает отдельный xray на порту 10801 (рабочий 1080
не трогает), спрашивает у **самого youtube.com** его `GL` (страна, которую видит Google), и
рядом печатает мнение `ipinfo`.

```
14 из 15 узлов: ipinfo говорит EU/US → YouTube всё равно отвечает GL=RU
узел [6/15] «Germany | Gemini»:      GL=DE, 374 мс   ← единственный годный
```

**Это объясняет, почему прошлый отбор узлов «по ipinfo» ничего не давал.** Критерий отбора
узла — только `GL` от youtube.com. Всё остальное — самообман.
Бот-чека (403) на немецком узле не прилетело.

### 2.8 Финальный замер: 100% живых треков

ZiziResolve 1.3 + немецкий узел, кэш сброшен:

## 3. Текущая архитектура

```
поиск/рекомендации:  APP ──Innertube──> music.youtube.com          (работает всегда)

воспроизведение:     APP ──/resolve|/stream──> VPS 147.45.166.244:8080
                                                 │
                                    ┌────────────┴─────────────┐
                              прямой путь                 прокси-путь
                          (IP сервера, GL=RU)          (xray → VLESS «Germany | Gemini», GL=DE)
                          бот-чек ПРОХОДИТ             гео ЧИСТОЕ, бот-чека нет
                          часть треков → 451/404-гео   206 на /stream, 130-170 КБ/с
```

Правило маршрутизации (ZiziResolve 1.3, `ZIZI_PROXY_MODE=fallback`):

1. резолв напрямую;
2. отказ `451 / 404 / 402 / 502` → повтор того же трека через прокси;
3. отказ `403` (бот-чек) → на прокси **не** идём, прямой IP тут сильнее;
4. трек, добытый через прокси, помечается `via=proxy`, и `/stream` для него тоже
   идёт через прокси (googlevideo привязывает ссылку к IP запросившего → иначе 403);
5. **не прошло нигде → спрашиваем `oembed`, и только он решает формулировку приговора:**
   `oembed 200` → `451` «недоступен из региона сервера», приговор **мягкий** (60 с);
   `oembed 404` → `404` «удалён или закрыт», приговор **жёсткий** (600 с);
   `oembed` молчит → приговор мягкий, потому что арбитр не подтвердил;
6. приложение (6.10.2) держит `451` у себя тоже 60 секунд, а `404/402` — 10 минут.

## 4. Ключевые технические факты (грабли, на которые не надо наступать снова)

1. **IP сервера геолоцируется Google как RU.** Нода в Амстердаме, но диапазон Timeweb
   российский: в ссылках `&gcr=ru`. Проверять это надо эндпоинтом `/geo`, а не догадками.
2. **`ipinfo` про VPN-узел ничего не значит.** 14 из 15 узлов «европейские» по `ipinfo`
   и российские по мнению YouTube. Единственный валидный тест — `GL` от youtube.com
   (`server/tools/zizi-geoscan.py`).
3. **`--xff US` / `geo_bypass` не работает.** Google закрыл трюк с `X-Forwarded-For`;
   в ответе он сам пишет `You might want to use a VPN or a proxy server (with --proxy)`.
4. **yt-dlp требует JS-движок И скрипты решателя.** Без пакета **`yt-dlp-ejs`** валится
   `n challenge solving failed`, и это выглядит как «This video is not available».
5. **Гео-блок и удаление у yt-dlp выглядят одинаково** (`Video unavailable`).
   Различать их можно только `oembed`. Не верить тексту ошибки — верить арбитру.
6. **IPv6 нельзя использовать.** YouTube душит IPv6-диапазоны ЦОДов. Нужны
   `source_address 0.0.0.0` (yt-dlp) и `local_address="0.0.0.0"` (httpx).
7. **Кэши yt-dlp для прямого и прокси-пути должны быть разными**
   (`ytdlp-cache/direct`, `ytdlp-cache/proxy`), иначе visitor-данные с RU-паспортом
   утекают в прокси-запрос.
8. **`--workers 2` у uvicorn = два независимых процесса**, у каждого свой кэш, свои
   приговоры и своя статистика. Нужен `--workers 1` (задача IO-bound, потерь нет).
9. **На сервере 890 МБ RAM, а не 4 ГБ.** Это была ошибка в прошлой версии этого документа,
   из-за неё OOM Deno выглядел мистикой. `Out of memory: Killed process (deno)
   total-vm:18145620kB` при нулевом свопе. Лечится свопом 2 ГБ +
   `DENO_V8_FLAGS=--max-old-space-size=256`. После лечения OOM в `journalctl -k` нет.
10. **Негативный кэш надо сбрасывать после любых изменений** (`/flush?neg_only=0`),
    иначе приложение получает приговоры, вынесенные до починки. В 1.3 это лечится
    конструктивно: мягкие приговоры живут 60 секунд.

6. **`/stats`** получил `soft_neg` / `hard_neg`.

## 9. Честные ограничения, которые не лечатся кодом

- **Треки, удалённые с YouTube, не играют.** `IM4v4sq8ypo` — именно такой случай, и это
  не наш баг: сервер честно это говорит и подтверждает арбитром.
- **Всё гео-плечо держится на одном VLESS-узле.** Он платный, и его могут забанить.
  Это не поломка кода, это качество подписки. Лечение — новый узел с `GL != RU`,
  находится за 8 минут скриптом `zizi-geoscan.py`.
- 890 МБ RAM — узкое место. Сейчас потолок ~190 МБ used при активной работе, запас есть,
  но два воркера или второй xray туда уже не влезут.
- Схема нарушает ToS YouTube. Репозиторий теоретически может получить жалобу.
- yt-dlp — гонка с Google. Именно поэтому резолв вынесен на сервер: там экстрактор
  обновляется ночным кроном силами сообщества, а не пересборкой APK.

## 10. Клиент 6.12.0 — скорость, память места, история поиска

Три вещи по замечаниям тестировщика и одна по багу. **Сервер не тронут**: `ZiziResolve 1.3` на
сервере остаётся тем же, `server/zizi_resolver.py` в этом ЗИПе ему соответствует побайтово.

### 10.1 Витрина (хаб) больше не ждёт сеть — `data/remote/HubCache.kt`

Было: каждое открытие «Поиска» = запрос `FEmusic_explore` в InnerTube с телефона, спиннер,
2–4 секунды на мобильном канале. Содержимое витрины меняется примерно дважды в сутки.

Стало: снапшот витрины лежит в `cacheDir` (`hub-<provider>.json`, до 512 КБ, версионированный).

| Ситуация | Поведение |
|---|---|
| Снапшот есть | Полки на экране за время парсинга JSON. Спиннера нет, трафика нет |
| Снапшот младше 30 минут | Запрос **не делается вообще** |
| Снапшот старше | Полки остаются, обновление идёт за ними, молча |
| Обновление упало | Снапшот остаётся. Вчерашняя витрина лучше плашки ошибки. Работает офлайн |
| Pull-to-refresh | Игнорирует свежесть, всегда идёт в сеть, но полки не убирает |

Формат пишется руками через `org.json`, с версией и правилом «нечитаемое = отсутствующее»:
битый или устаревший по формату файл не ошибка, а просто отсутствие кэша.
`«Очистить кэш потоков»` в настройках теперь чистит и его — иначе это была бы полуправда.

### 10.2 Память места — `SavedStateHandle`, а не файл настроек

Баг: свернул приложение на экране поиска или внутри плейлиста, система вытеснила процесс,
вернулся — медиатека, вкладка «Треки», всё сброшено.

Причина: `tab` в `MainActivity` был `rememberSaveable` (то есть переживал), а вот состояние
внутри `MainViewModel` и `SearchViewModel` жило в обычных `MutableStateFlow` и умирало вместе
с процессом.

Почему именно `SavedStateHandle`, а не DataStore: платформа **сама** стирает его, когда задача
завершена (пользователь закрыл приложение или вышел назад), и **сохраняет**, когда процесс просто
вытеснен из памяти. Это ровно то правило, которое нужно: «закрыл — начинаю с медиатеки, свернул —
вернулся на место». Никакого таймаута давности, который пришлось бы вечно подкручивать.

Что теперь переживает вытеснение процесса:

- медиатека: фильтр, открытый плейлист, открытая папка, поисковый запрос по библиотеке;
- поиск: строка, запрос, стадия, активная вкладка, открытый артист/альбом/плейлист;
- открытая шторка плеера (`playerOpen` → `rememberSaveable`).

Два решения, принятых осознанно:

- **Результаты поиска не сохраняются, сохраняется запрос.** Страница результатов — это до сотни
  элементов со ссылками на обложки, она устаревает, а переспросить стоит один запрос. Хранить надо
  место пользователя, а не ответ провайдера.
- **Стадия `SUGGEST` не восстанавливается никогда.** Вернуться в полунабранные подсказки с
  выскакивающей клавиатурой — это не «где я был», это испуг. Она сводится к `RESULTS`, если запрос
  был, иначе к витрине.

Запись состояния — **одним коллектором на `StateFlow`**, а не строчкой `saved[...] =` в каждом
мутаторе: `StateFlow` конфлейтит, так что это несколько строковых записей на действие
пользователя, зато ни один будущий вызов не может забыть себя записать.

Удалённый из другого места плейлист или отвязанная папка при восстановлении просто не открываются:
пайплайн библиотеки трактует неизвестный id как пустой выбор. Валидировать нечего, падать не на чем.

### 10.3 История поиска: 5 строк и свой скролл

Было: 20 записей истории рендерились как 20 элементов внешнего `LazyColumn` витрины. Чем больше
человек искал, тем ниже уезжали «Новые альбомы», пока витрина не перестала быть витриной.

Стало: до 5 записей — обычный столбик. Больше 5 — полоса фиксированной высоты со своим скроллом
и тонким индикатором справа (рисуется из `scrollState`, без библиотек и без обработки жестов).

Высота считается как `44.dp * fontScale` (с ограничением 1.0–1.6), а не забита как `220.dp`:
жёсткое значение обрезает последнюю строку при увеличенном системном шрифте — та же грабля, что
с фиксированными высотами шторок в этом файле. Вложенный вертикальный скролл внутри `LazyColumn`
легален именно потому, что высота задана.

### 10.4 Что НЕ сделано и почему (честно)

- **Серверный кэш витрины с ETag / 304.** Требует, чтобы сервер сам умел говорить с InnerTube
  (`FEmusic_explore` + кэш по хешу тела + `ETag` + `If-None-Match`), плюс правки клиента, чтобы он
  ходил за витриной через нас. Это осмысленно только вместе с общими лимитами и `/playlist`,
  то есть в **6.13**. Клиентский кэш из 10.1 уже снимает основную часть боли: при свежем снапшоте
  запроса нет вообще ни к нам, ни к Google.
- **Обмен плейлистами (`.zizi` + base64).** Спроектирован, не написан. Идёт следующей посылкой.
- **Обложки.** Проверил перед тем, как «оптимизировать»: `sizedUrl` уже перебивает размер в URL
  и просит у Google ровно 160 px для строк списка, плюс свой диск-кэш. Трогать нечего —
  тут уже сделано правильно.
